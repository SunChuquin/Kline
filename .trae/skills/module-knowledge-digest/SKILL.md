# 模块知识沉淀

## 这份文档写给谁

**未来的 AI 会话**（大概率是你自己），它没读过今天的对话，手上只有：
- 这份文档
- 代码本身
- 项目的 INDEX 索引

它读完应该能：定位到相关代码、理解为什么这么写、避开已知的坑。
**它不应该需要重读全部相关代码。**

## 三条铁律

1. **只写代码里看不出来的东西。**
   类名、方法名、参数、if 分支、显而易见的流程——一律不写。代码自己能说清楚的事，文档再说一遍就是噪音。

2. **文档长度不得超过它所描述的代码行数。**
   宁可少写，不可多写。写不下就拆成多篇，不要压缩成一篇巨长的。

3. **每条内容必须能回答"不写会怎样"。**
   答不上来的，删掉。

## 不写什么

- 对话过程（"我先…然后…"）
- 尝试过又放弃的中间方案（除非那个失败本身是个坑）
- 代码的复述、目录结构罗列、依赖清单
- 教科书式的背景介绍
- "本模块很重要""需要注意"这类无信息量的话

## 输出模板

输出需要结合"\.trae\skills\mermaid-doc-convention"技能

```markdown
## [模块名]

### 1. 它是什么 / 在哪
- 一句话职责
- 关键文件路径 + 关键类/方法名（精确到可跳转）
- 调用关系：谁调它 / 它调谁

### 2. 关键决策（为什么这么写）
- 每个非显然的设计选择：选了 A 而不是 B，因为…
- 引用具体现象 / 日志 / 历史坑

### 3. 已知陷阱
每条按这个格式：
- **现象** →
- **根因** →
- **现在的规避方式** →
- **关联代码位置**

### 4. 亮点 / 可复用的做法
- 值得其他模块借鉴的处理方式（只写非显然的）

### 5. 遗留 / 未验证
- [ ] 待验证项
- [ ] 已知但不修的边界情况
```

## 格式要求

- 涉及代码位置写 `文件路径:行号` 或 `类名.方法名`，方便下次直接跳
- 用 Obsidian 双链 `[[文件名]]` 关联已有文档，这是给未来 AI 拉上下文的入口
- 决策和陷阱分开写，不要混在段落里
- 不写大段散文，用列表和短句

## 归档约定

按内容性质分目录，不要全塞进一个文件：

```
modules/       架构事实、职责、调用关系
decisions/     关键决策，文件名带日期
pitfalls/      已知陷阱，一个坑一篇
observability/ 日志、监控、可观测性约定
```

写完更新 `INDEX.md`，把新文件挂到对应分类下。

## 交付流程

**不要一次写完。** 分两次交付：

1. 先写「1. 它是什么/在哪」和「2. 关键决策」，给用户确认
2. 确认后再写「3. 陷阱」「4. 亮点」「5. 遗留」

理由：每轮输出短、用户校对快、不容易跑偏成流水账。

## 交付前自检（必须回答）

1. 文档字数 vs 相关代码行数，比例是多少？超过 1:1 就删。
2. 未来 AI 只读这份文档 + 标注的关键文件，能不能改这个模块的常见需求？哪些需求它还得回去读代码？
3. 有没有哪段是"代码里能直接看出来的"？列出来，删掉。

自检结果和文档一起给用户，**用户确认后才写入文件**。
