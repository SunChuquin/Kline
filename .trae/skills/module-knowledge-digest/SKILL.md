# 模块知识沉淀

**本技能默认一次跑完**：用户给一句"用 module-knowledge-digest 沉淀今天关于 X 的文档"即视为已授权
——自行决定分几篇、每篇写什么、放哪个目录、提交信息写什么，**落盘并提交后一次性汇报**。
不要在中间停下来问"这节可以吗""要不要提成独立篇"。

## 这份文档写给谁

**未来的 AI 会话**（大概率是你自己），它没读过今天的对话，手上只有：
- 这份文档
- 代码本身
- 项目的 INDEX 索引

它读完应该能：定位到相关代码、理解为什么这么写、避开已知的坑。
**它不应该需要重读全部相关代码。**

## 三条铁律

1. **只写代码里看不出来的东西。**
   类名、方法名、参数、if 分支、显而易见的流程——一律不写。代码自己能说清楚的事，文档再说一遍就是噪音。

2. **长度：单篇硬红线 ≤ 它所描述代码的行数；全模块总量目标 ≤ 代码行数。**
   宁可少写，不可多写。写不下就**拆成多篇**，不要压缩成一篇巨长的。
   总量 1:1~1.5:1 可接受（多文件页脚与 `INDEX.md` 属索引开销），但必须在汇报里给出拆解 + 可砍位置；
   超过 1.5:1 必须删或再拆。

3. **每条内容必须能回答"不写会怎样"。**
   答不上来的，删掉。

**但以下三类必须写，哪怕代码里不显眼：**

- **跨模块判定** —— 例：悬浮按钮的显示范围由 `ContentView` 的 `selectedTab` 门控，本模块文件里根本看不到。
  不写，未来会话就会漏掉最关键的那条约束（"改了详情页呈现方式就失效"）。
- **行为机制** —— 例：触摸四态、各态外观取值、哪几个是稳定态。代码能看出实现，看不出**状态全景与迁移条件**。
  这类优先配一张图（见 `mermaid-doc-convention`）。
- **可调参数的集中位置** —— 例：几何/配色/时长各是一个常量数组。未来会话改需求时第一件事就是找它们。

## 不写什么

- 对话过程（"我先…然后…"）
- 尝试过又放弃的中间方案（除非那个失败本身是个坑）
- 代码的复述、目录结构罗列、依赖清单
- 教科书式的背景介绍
- "本模块很重要""需要注意"这类无信息量的话

## 输出模板

输出需要结合"\.trae\skills\mermaid-doc-convention"技能

```markdown
## [模块名]

### 1. 它是什么 / 在哪
- 一句话职责
- 关键文件路径 + 关键类/方法名（精确到可跳转）
- 调用关系：谁调它 / 它调谁

### 2. 关键决策（为什么这么写）
**本节只放「`[[双链]]` + 一行摘要」的索引，正文全部独立成篇放 `decisions/`。**

### 3. 已知陷阱
**本节同样只放「`[[双链]]` + 一行摘要」**，正文放 `pitfalls/`，每条按：
现象 → 根因 → 现在的规避方式 → 关联代码位置。

### 4. 亮点 / 可复用的做法
- 值得其他模块借鉴的处理方式（只写非显然的）

### 5. 遗留 / 未验证
每条除 `[ ]` 待验证项外，**必须补两行**：
- **怎么验**：具体到可执行动作（跑哪个 UITest、看哪两态的哪个环带、点哪里），不要写"需验证"
- **谁来验**：AI 可自验（编译/单测/CI）还是必须用户真机（外观、手感、性能）
```

每个 `decisions/` 、`pitfalls/` 篇的骨架：

```markdown
# <一句话结论，本身就是标题>（YYYY-MM-DD）

## 决策 / 现象
## 为什么（根因）
## 代价 / 现在的规避方式
## 关联代码
- `文件路径:行号`
- 相关篇：[[另一篇]]
```

## 格式要求

- 涉及代码位置写 `文件路径:行号` 或 `类名.方法名`，方便下次直接跳
- 用 Obsidian 双链 `[[文件名]]`（不带 `.md`）关联已有文档，这是给未来 AI 拉上下文的入口
- 决策和陷阱分开写，不要混在段落里（见下节）
- 不写大段散文，用列表和短句

## 决策 / 陷阱 / 架构事实：三者的去处不能混

| 内容性质 | 去处 | 判定 |
| --- | --- | --- |
| 职责、位置、装配点、调用关系 | `modules/<模块名>.md` | 代码里的**事实** |
| 选了 A 而不是 B，因为… | `decisions/` **独立成篇** | 代码里**看不出来**的原因 |
| 现象 → 根因 → 规避 → 位置 | `pitfalls/` **一个坑一篇** | 可复现的具体故障 |

- **决策必须独立成篇，哪怕只有三行。** 不允许以"另有几条不单独成篇的取舍"的形式埋在 `modules/` 正文里
  ——未来检索是按**文件名和标题** grep 的，埋在段落里等于丢失（例：搜 `dragDelta` 找不到它为什么不用 `@GestureState`）。
- 一条决策若由某个故障触发（例："必须先 `compositingGroup`"），**故障写 `pitfalls/`、理由写 `decisions/`**，两者用双链互指，不重复正文。
- `modules/<模块名>.md` 的第 2、3 节**只放「双链 + 一行摘要」**，不写正文。

## 归档约定

**位置已固定，不要问用户放哪**：本项目所有模块级知识都落在 `.trae/documents/<模块目录名>/`。

```
.trae/documents/<模块目录名>/          ← 目录名用英文小写（如 accessory）
├── INDEX.md                          ← 分类索引，写完必须更新
├── modules/<模块名>.md                ← 中文模块名，5 节主文档
├── decisions/YYYYMMDD-<模块名>-<主题>.md
├── pitfalls/YYYYMMDD-<现象简述>.md     ← 一个坑一篇
└── observability/<主题>.md            ← 无日志也要写一篇说明「暂无需要」及排障替代手段
```

- 与既有 `.trae/documents/Kline-*.md` 的分工：**模块级知识进子目录**；跨模块的规范/流程/方案类文档保持 `Kline-*.md` 平铺在原地。
- **文件名必须承载检索关键词**：写 `dragDelta用State而非GestureState`，不要写 `手势状态取舍`。
- 日期取**本次沉淀的日期**（`YYYYMMDD`）；同一模块同日多篇靠主题词区分，不编号。
- `observability/` 为空不算缺陷，但要写一篇一句话说明「当前无日志且暂无需要」+ 排障该用什么替代（例：UITest 断言而非插 print），否则未来会话会以为是漏写。
- **同一模块二次沉淀**：**追加到既有目录，不新建**。先读该目录的 `INDEX.md` 看已有什么，
  已有篇只增补不重写；确实推翻了旧结论就改旧篇并在标题下加一行「（已修订 YYYY-MM-DD）」，不要留两篇互相矛盾。

## 交付流程（默认一次交付，不逐节确认）

**一次把 5 节全写完并落盘，然后汇报自检。** 不要中途问"这节可以吗"。

只有这三种情况才提问，其余一律自行决定并在汇报里说明理由：

1. 沉淀对象**本身还没做完**（例：面板内容区是空的）—— 只能写进 §5 遗留，不许编造设计意图
2. 同一事实有两种**互相矛盾的**解读，且代码里看不出来（例：需求文字说 A=2D、括号示例说 A=2B）
3. 本项目没有任何既定归档形态可套（本项目的形态见上节，故通常不会触发）

**汇报格式固定为这 6 项，一次给全：**

1. **产出清单**：文件路径 + 行数表
2. **分篇理由**：哪几条提成了独立 `decisions/` 篇、为什么（避免下次又被埋在正文里）
3. **自检 4 项结论**（见下节）
4. **超标 / 偏离说明**：如总量超 1:1，给出拆解 + 具体可砍位置（写清砍哪一段，别说"可以精简"）
5. **未决项**：只能进 §5 的东西（还没做完的部分），以及要不要用户接着做
6. **提交哈希**

## 落盘后自动提交

**落盘后直接提交，不问用户。** 提交信息用**中文一句话**，不加 `type(scope):` 前缀
（那是代码提交的约定；文档提交的先例是 `补充辅助触控悬浮按钮相关文档`）。

- 只 `git add` 本次新增/修改的文档路径，**不要 `git add -A`**
- **不 push**（除非用户明确要求）
- 汇报里带上提交哈希

## 交付前自检（必须回答，与产出一起汇报）

1. **长度**：单篇最大 X 行 vs 代码 Y 行（红线 ≤ Y）；全模块总量 Z 行 → 比例 Z:Y。超 1:1 要给出拆解 + 可砍位置。
2. **未来 AI 只读这份文档 + 标注的关键文件，能不能改这个模块的常见需求？** 哪些需求它还得回去读代码？（列出来）
3. **有没有哪段是"代码里能直接看出来的"？** 列出来，删掉。
4. **每张 Mermaid 图**是否过了 `mermaid-doc-convention` 的自检清单（节点数、图前说明、图后补充、ASCII id）？
