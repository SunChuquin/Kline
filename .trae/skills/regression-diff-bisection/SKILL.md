# 回归问题差异分组二分法

已知「某个旧版本正常、之后某个版本出问题」，但静态读代码找不到根因时的标准打法：
**把好版本到坏版本之间的全部差异按功能分组，先全部屏蔽（等效回退到好版本），再逐组恢复——问题跟着哪一组回来，根因就在哪一组；组内继续二分直到具体函数/行。**

## 何时使用

- 用户明确指出「X 版本还正常，之后就坏了」，且 `good..bad` 之间存在多个提交或多条功能线；
- 静态审查、日志分析、自动化复现都未能定位（不要一上来就用，先做低成本排查）；
- 问题可由用户在固定设备上稳定复现，每轮能给出「在/不在」的二元判定。

不适用：好版本本身也坏；无法复现；差异只有一两行（直接读）。

## 核心原理

设差异被分成 G1、G2、G3… 若干组（按提交或功能线划分）：

1. **全部屏蔽 → 必须等效好版本**（关键闸门，见步骤 3）；
2. 每次只恢复一组，构建、按固定路径复现；
3. 问题**仍在** → 刚恢复的组无辜，保持恢复、继续下一组；问题**出现** → 根因在该组；
4. 锁定组后把组内改动再切成更小的块（文件 → 函数 → hunk），重复 2~3。

（反向操作「逐组注释、问题还在即排除已注释组」与上法等价，但「全屏蔽再恢复」有一个
不可替代的好处：它先验证了「差异确实能解释问题」这个大前提，见陷阱 1。）

## 标准步骤

1. **锚定两端**：与用户确认好版本号/提交 `GOOD`（如 CI #430 = `6527ada`）、坏版本 `BAD`（通常是 HEAD）。
   `git log --oneline GOOD..BAD` 列提交，`git diff --stat GOOD..BAD` 列文件。
2. **分组**：一个提交一组最省事；一个提交混多功能时按「功能线/调用链」拆。
   每组登记：组名、提交、文件清单、屏蔽方式、验证结果（先空着）。
3. **基准闸门（最重要的一步）**：把**所有组全部屏蔽**，构建出「等效 GOOD」的二进制，让用户在**同一设备、同一复现路径**上验证：
   - 问题**消失** → 证明根因在代码差异内，继续二分；
   - 问题**仍在** → **立即停止分组**，根因不在这批代码里，转查陷阱 1 的清单（数据/持久化状态/构建配置/环境）。
4. **逐组恢复**：每次只放开一组，可编译 → 安装 → 用户复现 → 记录判定。复现路径每轮必须完全一致。
5. **组内二分**：锁定嫌疑组后，按文件 → 函数 → hunk 继续切，每次只放一半，直到定位到具体代码。
6. **收尾**：定位后只保留真正的修复，其余屏蔽的代码全部还原；`git diff` 确认工作区只剩「修复 + 用户原有需求改动」。

## 屏蔽手段（按优先级）

1. **功能开关 / 注释调用点**（首选）：新逻辑多由按钮、定时任务、`.onAppear`、订阅触发，注释触发点即可让新代码成为死代码，改动最小、最易还原。
2. **整文件回退到 GOOD**：对被修改的旧文件用 `git checkout GOOD -- <file>`（先备份当前版到临时分支或 patch：`git diff GOOD..BAD -- <file> > /tmp/gN.patch`）。
3. **新文件断引用**：新文件从 target 移除或改名使其不参与编译；调用点用空实现桩替代（`func x() {}` / `return 原值`），保证其余代码可编译。
4. **函数体打桩**：注释整段会引发连锁编译错时，保留签名、函数体直接 `return` 中性值。

每一步都必须**独立可编译**；宁可多打几个桩，也不要留下半注释的烂摊子无法二分。

## 分组原则

- 按「用户可感知的功能」分组，不要按文件机械切（同一功能跨多文件要算一组，否则单独恢复任一组都编译不过/无法验证）；
- 一组内的改动必须能被**独立屏蔽且其余组仍可运行**——有依赖时把有依赖的两组合成一大组先切；
- UI 层改动（视图/手势/覆盖层/标识符）与数据层改动（DB/网络/后台任务）尽量不同组，嫌疑权重不同。

## 陷阱

1. **「全屏蔽」后问题仍在**：根因在代码差异之外，常见有——① 沙盒数据被新版本的数据迁移改写（删表重写、格式升级，**不可逆**，回退代码也读旧数据的新形态）；② UserDefaults/持久化 JSON/落位点被改写；③ 构建配置差异（Debug/Release、签名、entitlements、Info.plist、构建号）；④ 安装残留（覆盖安装、TrollStore 未删净）；⑤ 设备/系统状态（键盘、辅助功能、前台保活的老进程）。验证手段：全新模拟器（`simctl erase`）或删 App 重装 GOOD。
2. **数据迁移不可逆**：屏蔽前先备份设备数据容器（模拟器：`get_app_container` 整目录拷贝），否则二分过程会污染现场、无法回头。
3. **测试 target 干扰**：新增的 UITest/单元测试文件不进 App 产物，不要把「测试失败」误判为 App 回归；但 PBXFileSystemSynchronizedRootGroup 工程里新文件会**自动入 target**，屏蔽新文件时要真的移除成员而非只删引用。
4. **复现路径漂移**：用户每轮操作顺序、点击位置（尤其避开/包含悬浮按钮等覆盖层）、横竖屏必须一致；最好让用户按书面步骤操作并保留 `debug_log.txt`。
5. **被自己的临时插桩误导**：排查中加的探针/日志/测试在定位后必须全部删除，不能混进结论。
6. **自动化不可信时的退路**：自动化测不出但用户能复现，说明真人手势时序/数据状态是必要条件——二分时以用户判定为准，不要用「自动化通过」否定用户结论。

## 与 git bisect 的关系

- 提交历史干净（每提交单一功能、且每个中间提交都可构建）时，直接 `git bisect` 更快；
- 一个提交混多功能、或中间提交不可构建/不可运行时，用本方法按功能分组；
- 两者可以组合：先 bisect 到嫌疑提交，再对该提交做组内 hunk 二分。

## Kline 项目落地要点

- 好/坏版本号优先用 **CI 构建号**对照提交（GitHub Actions run number → head_sha）。
- 验证设备固定为 **iPad mini 5th 模拟器**（UDID `54291852-68BE-45BF-ACC0-72CEAEF10A0B`），模拟器窗口必须对用户可见，严禁 headless；
  真机链路是 CI Release + TrollStore，注意 Debug/Release 与签名差异。
- xcodebuild 必须**非沙箱**执行，否则 #Preview 宏插件被拦（报 macro implementation not found）。
- 数据容器路径随 `simctl install` 变化，每轮先 `xcrun simctl get_app_container <UDID> com.sunck.Kline data` 重取；
  日志固定在容器 `Documents/debug_log.txt`。
- 数据层嫌疑（主库 `tdx.db` 1.4GB、增量库 `tdx_live.db`、周期表重建/缺口补齐）在屏蔽前**先整容器备份**，这类迁移多为不可逆。
- 每轮构建安装用闭环脚本 `bash scripts/kline_deploy_mac.sh`；但二分期间**不要让脚本提交代码**（大量临时屏蔽不该入库），
  直接 `xcodebuild build` + `simctl install/launch`，定位并修好后再走一次闭环提交。
