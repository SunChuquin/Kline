# 增量库扩展到全市场（日分片 + 两个生产者 + 合并回主库）Spec

## Why

现有增量库只覆盖 `symbols.txt` 里的 19 只标的，导致**打开任何未列入的标的仍是主库的 2026-08-28**。用户要求：覆盖 `tdx.db` 里全部标的（3611 只）、工作日 3 个时刻点自动更新、个人中心手动触发、并可手动「合并」把增量写回 `tdx.db`。

关键事实（实测，来自 PC 上的 `C:\Users\sunck\home\tdx.db`，与设备主库同一份，1379.7MB）：

| 项 | 实测值 |
| :--- | :--- |
| meta 行数 | **3611**（沪深主板 3193 / 扩展行情指数 299 / 沪深京指数 119） |
| `code` 唯一性 | ❌ 3556 distinct / 3611（55 处重复：指数与股票同码，如 `62#000995` 全指公用 vs `SZ#000995` 皇台酒业） |
| `file` 唯一性 | ✅ 3611/3611（`SH#600000`、`SZ#000995`、`SH#000009`、`27#HSBIO`） |
| 主库 last_date | 全部 = **20260828**（缺口约 17 个交易日） |
| 可映射公开行情接口 | **3312**（`SH#/SZ#/BJ#` 前缀）；**299 只扩展行情指数不可映射**（恒生/行业指数） |
| daily 行数 | 14,008,185 |

结论：**键必须用 `file`**（唯一 + 前缀自带市场语义）；**299 只扩展行情指数只能靠本机通达信数据生产**。

## What Changes

- **键从 `code` 改为 `file`**（生产者与 App 双侧）。
- **分片粒度 = 1 个交易日**（`bucket_id = unix 日序`），单片约 **0.5MB**；保留最近 **30 片**（≈6 周）。
- **清单来自 `src/data/universe.txt`**（从主库 meta 导出 3611 行），不再云端枚举全市场、**不再做逐标的历史补齐**。
- **两个生产者，同一份日分片格式，谁跑谁生效**：
  1. **电脑侧（首选，`source: pc_tdx`）**：读本机 `tdx.db` 最近 N 天 → 出日分片 → 直接推设备或推 `data` 分支。零网络、秒级、**唯一能覆盖 299 只扩展行情指数**。
  2. **云端（兜底，`source: eastmoney`）**：读 `universe.txt` 的 3312 个可映射标的 → 批量快照出"当天那一片"（约 34 次请求）。
- **App 按缺口取片**（典型 1 片 ≈0.5MB），合并进本地增量库并裁剪冗余行。
- **新增「合并到 tdx.db」**：二次确认 → 事务内按 `(meta_id, date)` 主键 UPSERT（`file → meta_id` 映射）→ 更新 `meta.last_date`。
- 增量库收敛为 **daily/weekly/monthly** 三表（季/年无法被有限窗口完整覆盖，回落主库）。

## Impact

- `src/live_db_builder.py`（云端生产者，改为 universe + 日分片）、`src/data/universe.txt`（新增）、`.github/workflows/sync-live-db.yml`
- 新增 `TrollRestore/build_live_buckets_pc.py`（电脑侧生产者）
- `Kline/Data/LiveDataStore.swift`（键改 file + 可写合并 + 裁剪）、`Kline/Data/DatabaseManager.swift`（合并查询键改 file）
- `Kline/Infrastructure/TdxSyncManager.swift`（manifest schema 3 + 取片）
- `Kline/Data/MainDBMerger.swift`（新增，合并回主库）、`Kline/Profile/LocalUpdateView.swift`（合并按钮 + 覆盖率）
- 主库 `tdx.db` 仍不被自动替换；合并是用户显式动作、只在主键上 UPSERT、不删历史

## 契约（v3）

### 1. 清单 `src/data/universe.txt`

TAB 分隔：`file / code / name / type`，3611 行，含 `file 前缀 → secid` 映射说明的注释头。

| 前缀 | secid | 数量 |
| :--- | :--- | ---: |
| `SH#xxxxxx` | `1.xxxxxx` | 3193 + 部分指数 |
| `SZ#xxxxxx` | `0.xxxxxx` | 沪深主板 |
| `BJ#xxxxxx` | `0.xxxxxx`（北交所） | 若有 |
| `27#` / `62#` / 其他 | ❌ 无对应 | 299（仅电脑侧可覆盖） |

### 2. 分片与 manifest

```
live/manifest.json
live/bucket_<bucket_id>.db      # bucket_id = (date - date(1970,1,1)).days，例 20260922 → 20718
```

分片表结构（表名固定，两端契约）：

```sql
bkt_meta(file TEXT PRIMARY KEY, code TEXT, name TEXT, type TEXT, updated_at INTEGER);
bkt_daily (file TEXT, date INTEGER, open REAL, high REAL, low REAL, close REAL, vol REAL, amo REAL, PRIMARY KEY(file, date));
bkt_weekly / bkt_monthly 同构
```

- 一片 = **一个交易日**（`min_date == max_date`），不重叠。三张表（`bkt_daily/bkt_weekly/bkt_monthly`）**在每片里都必须存在**，即使该表为空——App 用 ATTACH/UNION 合并时不应因缺表失败。
- **只发 daily/weekly/monthly**；周/月线**只要"周期首日"落在发布窗口内就发**（**完整周期与进行中的周/月都发**，见 §7）；
  周期首日在窗口起点之前的周/月线**不发**（那时既算不出正确的"周期首日"、聚合值也只是局部，会污染主库）。
- 保留最近 **30 片**，超出者在发布时删除。
- manifest（**schema 3**）：

```json
{"schema": 3, "generated_at": 1790048739, "trade_date": 20260922,
 "source": "pc_tdx", "universe": 3611, "covered": 3611, "coverage": 1.0,
 "missing_sample": ["27#HSBIO"],
 "latest_bucket": 20718, "keep_buckets": 30,
 "buckets": [{"file": "bucket_20718.db", "id": 20718, "min_date": 20260922, "max_date": 20260922,
              "bytes": 512000, "sha256": "...",
              "rows": {"daily": 3312, "weekly": 240, "monthly": 12, "meta": 3611}}]}
```

`buckets` 按 id 从新到旧。首片之外的历史片**按天逐个累积**（不回溯补齐）。

### 3. 生产者

**A. 电脑侧（首选）`TrollRestore/build_live_buckets_pc.py`**（新增，纯 stdlib）
- 只读打开 `C:\Users\sunck\home\tdx.db`（**绝不修改**；用 `file:...?mode=ro` URI）；
- 读 `src/data/universe.txt` 的 3611 个 `file`，用 `meta.id` 关联取出 `daily` 最近 N（默认 30）个交易日；
- 本地聚合出 weekly/monthly（周期首日落在窗口内就发，含进行中的周/月，口径见 §7）；产出对应日分片到 `--out`；
- 幂等：内容相同的分片不重写；支持 `--push-usb` / `--push-lan <host>`（逐片推设备）或 `--publish`（提交到 `data` 分支）；
- 覆盖面 = 3611/3611（含 299 只扩展行情指数）；**零网络请求**。

**B. 云端（兜底）`src/live_db_builder.py` + `.github/workflows/sync-live-db.yml`**
- 读 `universe.txt`，仅 `SH#/SZ#/BJ#`（3312 只）→ secid；`27#/62#` 跳过并计入 `missing_sample`；
- 每档：批量快照（`ulist.np/get`，secid ≤100/批 → 约 34 次请求）取当日那根 → 写/更新当天分片；
- 从 `data` 分支读回旧分片以保留最近 30 片；日常路径**只产出当天那一片**，不做历史补齐；
- 覆盖率 < 0.85 判失败（保留上一版）；无新增K线则跳过发布（退出码 0，`dist/.changed=0`）。

**B2. 一次性缺口回补 `--backfill-days N`（默认 0=关闭，只在补历史缺口时手动跑一次）**

为什么需要：设备主库停在 2026-08-28，而"当天那一片"只能让人一天一天往前爬。`--backfill-days N`
把最近 N 个交易日的日线**一次性**补齐，直接把这段缺口灌满。

- 取数：逐标的 `push2his.eastmoney.com/api/qt/stock/kline/get?secid=…&klt=101&fqt=1&lmt=N`
  （`fqt=1` 前复权，与主库口径一致；字段顺序是 **开,收,高,低**，见 `_parse_kline_line`）；
- 礼貌并发：`ThreadPoolExecutor`，`--workers` 默认 4（上限 8），**总速率由全局限速压在约 4 请求/秒**
  （0.25s 间隔，线程安全的"预约时间槽"实现）；每只失败重试 4 次（指数退避），
  单只失败只计入 `missing`，不中断整体；每 300 只打印一次"已完成/总数 · 成功/失败 · 耗时 · 预计剩余"；
- 产出与日常**完全同构**：同样的 `bucket_<id>.db` 三表、周期用"周期首日"口径、只发首日在窗口内的周期；
  与 `--prev` 的旧分片合并（同 `file+date` 以新数据为准），只回写**变化过**的分片，保留最近 30 片；
- `27#/62#/102#` 等不可映射标的**跳过**（这段缺口它们本来就补不上，计入 `missing_sample`），
  日志会明确写出"需由电脑侧生产者覆盖"；
- `--limit-symbols N` 仅调试用（只处理前 N 只，并跳过覆盖率门槛）；
- **定位：一次性**。补齐后由日常三档继续往前滚；不要把它写进 cron（3312 次请求、约 15 分钟）。

### 4. App 取片策略

1. `needFrom` = `metaList` 中 `lastDate` 的最大值（全空 → 最新分片的 `min_date`）；`needTo` = 今天。
2. 取区间相交的分片，id 从新到旧，**上限 30 片**；典型 **1 片 ≈0.5MB**；无需下载则标记"主库已是最新"。
3. 逐片：下载 → sha256 校验 → 合并进 `tdx_live.db`（`INSERT OR REPLACE`，键 `file`）→ 全部完成后**单次**热刷新。
4. 合并后裁剪本地增量中 `date <= 主库该标最新 date` 的行。
5. 任一片失败 → 整体失败、保留原状，错误写明"第几片(bucket_id)"。

### 5. 本地增量库（App 侧）

```sql
live_meta(file TEXT PRIMARY KEY, code TEXT, name TEXT, type TEXT, updated_at INTEGER);
live_daily(file TEXT, date INTEGER, open, high, low, close, vol, amo, PRIMARY KEY(file, date));
live_weekly / live_monthly 同构
```

合并查询：`metaId → file`（`MetaItem.file`）→ 增量行优先，同 `date` 以增量为准，其余取主库。

### 6. 「合并到 tdx.db」

- UI：个人中心「数据同步」分区按钮；同步中/无可合并行时禁用。
- 点击 → 二次确认弹窗（显示"将写入 N 根K线 / 覆盖 M 只标的 / 最新交易日 YYYYMMDD"）。
- 确认后（`dbQueue` 上、单事务）：`file → meta_id` 映射 → 对 daily/weekly/monthly **存在才写**的 `INSERT OR REPLACE`（prepared statement 循环 bind）→ 更新 `meta.last_date` → 提交；返回"写入行数 / 命中标的数 / 跳过（主库无此 file）数 / 最新交易日"。
- 不删主库任何历史行；失败 `ROLLBACK` 并保留增量库原样；完成后 `loadMetaList()` + 增量裁剪（保留最新 3 个交易日缓冲）。

### 7. 周/月线口径（与主库对齐，逐条实测于 2026-09-22）

| 项 | 规则 | 主库实测依据 |
| :--- | :--- | :--- |
| `date` | **该周期的第一个交易日**：周线 = 该 ISO 周内**该标的**的第一个交易日；月线 = 该月第一个交易日 | SH#600000 周线 `20260824` 覆盖 0824~0828（周一为首日）、月线 `20260803` 覆盖 0803~0828；27#HSCEI / 27#HSI / 62#000995 同；由 daily 按 ISO 周推出的"周期首日"序列与主库 weekly 的 date 序列**完全一致** |
| 数值 | 该周期从**首日**起、到周期末（进行中的周期则到窗口内该周期最后一天）的全部日线聚合：`open`=首根 open、`high`=期间最大、`low`=期间最小、`close`=末根 close、`vol/amo`=求和 | 与主库 weekly/monthly 行**逐字段一致**（含 `20260803` 这根"进行中"的 8 月月线） |
| 发出条件 | **周期首日落在发布窗口内就发**，**包含进行中的周/月**（通达信盘中就显示"本周这根K线"）；周期首日在**窗口起点之前** → **不发** | 窗口最旧那片之前没有日线，算不出真正的周期首日（date 会错、合并回主库会插重复行），聚合值也只是局部 |
| 落片 | 按 `date`（=周期首日）落到该日的日分片；因此一次运行可能同时更新「当天片 + 本周首日片 + 本月首日片」 | 见 `build_slots` |

- ⚠ **一律不要改成"周期末日"做 `date`**：与主库 `(meta_id, date)` 主键对不上，合并回主库会**多插一行重复的周/月线**。
- ⚠ 窗口起点天然兜住"第一周/第一月"：`--days 20`（窗口 20260803~20260828）里，最新片含本周首日
  `20260824` 的周线与 8 月首日 `20260803` 的月线；而窗口起点之前的那个半周（≤0731 属于 0727 那周）不发。

## Scenario

#### 场景：任意标的都变新
- **WHEN** 用户打开任意一只主库里的标的
- **THEN** K线最后一根 = 最近一次同步的交易日（数据来自全市场增量库，键为 `file`），不再停在 08-28

#### 场景：只取当天那一片
- **WHEN** 主库最新为 09-22、今天 09-23、云端已发布 09-23 的分片
- **THEN** App 只下载 `bucket_<09-23>.db`（约 0.5MB），不再下载其它片

#### 场景：缺口补齐
- **WHEN** 主库停在 08-28，今天是 09-22，云端/电脑侧已发布这段每个交易日各一片
- **THEN** App 下载相交的那 17 片并合并，图表日期连续无空洞

#### 场景：电脑侧补上接口覆盖不到的指数
- **WHEN** 用户在电脑上跑 `build_live_buckets_pc.py --push-usb`
- **THEN** 3611 只（含 299 只扩展行情指数）当天K线写入设备，覆盖率 100%

#### 场景：合并回主库
- **WHEN** 用户点「合并到 tdx.db」并确认
- **THEN** 主库中这些标的最新K线变为增量库最新交易日、`meta.last_date` 同步更新；重开 App 数据仍正确

## 风险与边界

- **扩展行情指数**：云端永远无法覆盖（公开接口无对应），只有电脑侧生产能覆盖；面板以覆盖率体现。
  **缺口回补也补不了这 299 只**：`--backfill-days` 只作用于可映射的 3312 只，`27#/62#/102#`（恒生/行业/主题指数）
  会被跳过并写进 `missing_sample`；它们的缺口只能等电脑侧生产者产出（读本机通达信数据）。
- **季/年线**：不再发布，视图回落主库（最新未完成周期可能滞后）。
- **主库写入**：几万行 UPSERT 走主键索引，秒级；二次确认 + 事务防误操作。
- **仍需前台**：所有通道生效前提不变（Kline 前台未锁屏）。
- **首次缺口（08-29~09-22，17 个交易日）**：**云端即可补齐** —— 手动跑一次
  `--backfill-days 17`（或 30）把这段灌满（覆盖可映射的 3312 只）；那 299 只扩展行情指数仍需电脑侧生产者产出
  （或先在通达信客户端补一次导出再跑电脑侧生产者）。日常三档只往前滚，不会再碰这段历史。

全部为 2026-09-22 在真机/真库上跑出来的数字（主库 `C:\Users\sunck\home\tdx.db` = 1379.7MB，

### 主库口径（先测清楚，否则合并回主库会写错行）

| 项 | 实测 |
| :--- | :--- |
| meta / daily | 3611 行 / 14,008,185 行；`file` 3611 唯一、`code` 3556 distinct（55 处重复）|
| 可映射 vs 不可映射 | 3312（SH#1756 + SZ#1556）/ 299（62#250 + 27#26 + 102#23）|
| `last_date` | 3611 行**全部** = 20260828（daily 最大日期同为 20260828）|
| **周线 `date`** | = 该 ISO 周内**该标的的第一个交易日**（SH#600000 周线 20260824 覆盖 0824~0828；周线值 = 这 5 根日线聚合）|
| **月线 `date`** | = 该月**第一个交易日**（SH#600000 月线 20260803 覆盖 0803~0828）|
| 主库是否发"进行中"周期 | **发**（8 月未走完，20260803 那根月线已存在）|
| 通达信伪代码 | 只有 `SH#999999` 一个（上证指数，东财 secid = `1.000001`），已进 `SPECIAL_FILE_SECID` 特例表 |

### A. 电脑侧生产者 `build_live_buckets_pc.py`（首选，零网络，覆盖率 3611/3611）

| 运行 | 片数 / 日期范围 | 每片体积 | 总字节 | 覆盖率 | 耗时 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `--days 3` | 3 片 20260826~20260828 | 643,072 B ≈ 628 KB | 1.84 MB | 3611/3611 | 13.8s（读库 0.6s + 两次主库 sha256 12.4s）|
| `--days 18` | 18 片 20260805~20260828 | 643,072~978,944 B | 12.3 MB | 3611/3611 | ~15s |
| `--days 20` | 20 片 20260803~20260828 | 643,072~978,944 B | 13.22 MB | 3611/3611 | 14.8s |

- 每片 `meta` = 3611 行（分片自包含）；`daily` = 该日有行情的 file 数（3606~3611，差异是停牌标的）。
- 主库只读校验：三次运行 sha256 + mtime + size **全部一致**（读侧只额外生成 `-shm`/`-wal`）。
- 幂等：同窗口重复构建逐片 sha256 完全一致；同目录重跑「本次重写 0 片」。
- 分片 id：4 次不同窗口运行、20 个日期，同一 `date` 始终同一 `bucket_id`，且各片 `date` 两两不同（无重叠）。

| :--- | :--- |

### C. 缺口结论（关键，决定了缺口怎么补）

- 主库 daily 最大日期 = **20260828**；`date > 20260828` 的行数 = **0**；`date = 20260922` 的行数 = **0**。
- `--days 20` 产出 20260803~20260828；**20260829~20260922（17 个工作日）没有任何分片文件** ——
  是"**整片缺失**"（源数据里根本没有这些日子），不是"空片"。
- **结论：电脑侧生产者无法凭自身补上 08-29~09-22 的缺口**，因为它读的就是那份停在 08-28 的主库。
  补缺口只有两条路：① 先在通达信客户端补一次数据导出（让本机库走到今天），再跑电脑侧生产者；
  ② 由云端按天往前滚动（从今天起每天一片，历史缺口不回补）。

### D. 周/月线口径与"进行中周期"实测

- **口径**（详见 §7）：`date` = **周期首日**（周线 = 该 ISO 周内该标的的第一个交易日；月线 = 该月
  第一个交易日）；数值 = 该周期首日起、到窗口内该周期最后一天的全部日线聚合。
- **发出条件**：周期的候选首日（日历起始日**向后跳过纯周末**，如 8 月：0801 周六 → 0803）
  落在窗口起点之后或正好是它 → **发**（**含进行中的周/月**）；落在窗口起点之前 → **不发**
  （那时 date 会算错、聚合值只是局部，会污染主库）。
- **决定性校验**：把 `--days 20`（窗口 20260803~20260828）产出的周/月线，与主库 `tdx.db` 自己的
  `weekly`/`monthly` 按 `(file, date)` 逐字段比对 ——
  **产出 18,051 行；逐字段完全一致 18,051 行；不一致 0、多出 0、缺失 0**
  （weekly 14,440 + monthly 3,611）。即"日期=周期首日、数值=周期日线聚合、每周一根"三条同时成立。
- **新旧规则对比**（同一窗口）：旧规则（只发完整周期）下，最新一周的周线（`date=20260824`，3,608 行）
  与 8 月月线（`date=20260803`，3,606 行）**一行都没有**；新规则下都有了 → 周/月线不再滞后一个周期。
- **落片位置（容易误解）**：周/月线按自己的 `date` 落到**那一天的日分片**，所以
  `date=20260824` 的周线在 `bucket_20689`(0824)、`date=20260803` 的月线在 `bucket_20668`(0803)；
  最新那片 `bucket_20693`(0828) 的 `weekly` 只有 **1 行** —— 那是"该标的本周首个交易日恰为
  0828（周五，前四天停牌）"的情况，主库同款（`SELECT COUNT(*) FROM weekly WHERE date=20260828`
  同样是这些标的）。**周/月线不会被塞进"最新那片"。**
- ⚠ 取片细节：周/月线的 date 是周期首日，所以 App 的 `needFrom`（主库 meta 的最大 `last_date`）
  若落在周期中间（例如主库停在周三 0826），`date < needFrom` 的那根周期线所在分片不会被下载 ——
  此时主库自己那根周期线仍在（值可能偏旧）。主库停在周五或周期首日时不触发。
- 该窗口总字节：13.867 MB（旧规则 13.223 MB → 去掉 `cal_end` 限制 13.543 MB → 再补周末感知 13.867 MB）。

### E. `--check`（v3）检查项

schema=3 / 片数 ≤30 / 每片 rows·bytes·sha256 与 manifest 逐项一致 / 片内 `min_date == max_date == 分片日期` /
分片间日期不重叠 / 最新片含 `trade_date` / 输出目录无 manifest 未声明的多余分片；并打印每片体积与总字节。
实测：pc3 / pc20 / pc20c / v3_net3 / v3off2 均「全部校验通过」（退出码 0）；篡改一根 K 线或放入未声明的分片 → 退出码 1。

**空表也要存在**：`build_bucket_file` 对 `bkt_meta/bkt_daily/bkt_weekly/bkt_monthly` 四张表一律
无条件 `CREATE`，只在有数据时才 `INSERT`。实测 `--days 20` 的 20 个分片里，
10 片的 `bkt_weekly` 为 0 行、16 片的 `bkt_monthly` 为 0 行，但**四张表全部存在**
（`bucket_20693.db` = `bkt_meta` 3611 / `bkt_daily` 3611 / `bkt_weekly` 1 / `bkt_monthly` 0 行），
App 侧 ATTACH/UNION 合并不会因缺表失败。`--check` 不含"周期必须完整"之类的断言（只校验行数与日期），
因此进行中的周/月不会被误判为错误。
