# 下载设备文件返回的 503 是「本机代理」造成的假象（2026-09-23）

## 现象

`GET /sandbox/tdx.db`（1.4 GB）返回 **HTTP 503 Service Unavailable**，看起来像服务器拒绝了大文件。

但查服务器代码后确认：`KlineHTTPServer.respond` 的状态分支**只有 200 / 400 / 404 / 500**，
**根本不会返回 503**。

## 根因

本机环境有 `HTTP_PROXY=127.0.0.1:10808` 且 **`NO_PROXY` 为空**，
`urllib.request.urlopen("http://127.0.0.1:5051/...")` 会**把回环地址也走代理**，
代理拒绝该目标 → 回给客户端一个 **503 假象**。

（`TrollRestore/build_and_deploy.py:108` 的注释里早有这条记载，我这次又踩了一遍。）

**实测判据**：
- 默认 `urlopen` 访问 `127.0.0.1:59999`（一个没人监听的端口）→ 返回 **HTTP 503**
- 换成 `urllib.request.build_opener(urllib.request.ProxyHandler({}))` → 得到真实结果 `WinError 10061`（连接被拒）

—— 访问无人监听的端口却拿到 503 而不是连接错误，就是代理在应答的铁证。

## 现在的规避方式

PC 侧所有走本地 HTTP（usbmux forward → 设备 5051）的脚本，**必须全局绕代理**：

```python
import urllib.request
urllib.request.install_opener(urllib.request.build_opener(urllib.request.ProxyHandler({})))
```

用 `install_opener` 而非逐个 `urlopen` —— 这样 `sandbox_cli.check_online`、
`push_live_usb.http_put`、`push_bucket_usb.http_request` 等**一并生效**。

已落地的脚本：`verify_main_db.py`、`sync_pipeline.py`。

另外顺带修掉一个真问题：`serveSandboxPath` 原先用 `readDataToEndOfFile()` 把整份 1.4 GB
读进内存再一次性 `send` —— 已改为 **1 MB 分块 `FileHandle` 读 + 顺序 `send`**（只占 1 块内存）。
