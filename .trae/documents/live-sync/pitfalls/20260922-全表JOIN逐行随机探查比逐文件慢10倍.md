# 覆盖全库的一条大 JOIN，比逐文件局部核对慢约 10 倍（2026-09-22）

> 这是「把 400 秒压到 138 秒」的唯一原因。改 `diff_live_patch.py` 的差异扫描前务必先读。
> **注：这只是三层优化里的第①层**——最终 400.0s → **7.0s** 还靠「变更裁剪」与「固定开销按需化」，
> 完整的三层拆解见 [[复权差分重灌通道]] §9。

## 现象

差分生成器原实现用**一条覆盖全库的 SQL** 求差异：

```sql
SELECT ... FROM main.daily n
JOIN main.meta nm ON nm.id = n.meta_id
JOIN base.meta bm ON bm.file = nm.file
JOIN base.daily b ON b.meta_id = bm.id AND b.date = n.date
WHERE <任一字段变化>
```

在 1.4GB / 1400 万行的库对上，**单是 daily 一个周期就要 208 秒**，全跑（含 weekly/monthly/quarterly/yearly）差异扫描 **386.7 秒**。

## 根因

`EXPLAIN QUERY PLAN` 显示：`SCAN n` + 每行一次 `SEARCH b USING INDEX (meta_id=? AND date=?)`。
即**对 1400 万行各做一次随机索引探查**（探查完还要回表取 8 个字段）。

两个反直觉的实测结论：

| 试验 | 耗时 | 说明 |
| :--- | ---: | :--- |
| 现状 4 表 `file` 关联 | **208.7s** | |
| 去掉 2 次 meta 探查（`meta_id` 直连） | **194.4s** | **只快 7%** → 瓶颈不是「JOIN 有几层」 |
| `COUNT(*)` 纯走索引 | 0.6s | 顺序扫索引极快 |
| `SUM(close)` 需读行 | 4.1s | 顺序读全表行也只有 4 秒 → **顺序 ≠ 随机** |
| 强制顺序扫 + GROUP BY 签名 | 38.1s | 也不如逐文件 |

所以慢的不是数据量、也不是关联层数，而是**访问模式的随机性**。

## 现在的规避方式

**逐文件局部核对**：把大 JOIN 换成对每个 file 单独执行

```sql
SELECT n.date, ..., (b.date IS NULL)
FROM main.<period> n LEFT JOIN base.<period> b ON b.meta_id = ? AND b.date = n.date
WHERE n.meta_id = ? AND (b.date IS NULL OR <任一字段变化>)
```

`WHERE n.meta_id = ?` 让两侧的索引探查都落在**同一个 file 的连续页内**（全部命中缓存）。

- 实测 **0.005 ~ 0.02s/只** → 3611 只 daily ≈ 67.5s（原 208s）
- 一条 SQL 同时拿「改写」与「主库新增」（`b.date IS NULL` 即新增）
- `base_only` 不必再扫基线一遍，由行数差推出：`base_only = base_cnt - (main_cnt - new_only)`
- 关联键仍是 `file`（两库 id 各自按 `file` 从自己的 `meta` 查出，只用于定位）

**注意**：实测「每文件固定开销」可以忽略（3611 次极小查询共 0.05s），
所以按块 `IN (?,?,...)` 批处理并不能进一步加速（实测 600 只批处理反而更慢）。
剩下的耗时是**逐行 CPU/IO 的固有成本**，要再快只能靠「少比一些文件」（见 [[复权差分重灌通道]] §9）。
