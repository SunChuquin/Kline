# 换了「同规模」的库当基线，产出千万行假差异（2026-09-22）

> （已修订 2026-09-22：原写「meta 按字母序重排」，实际是**被重新编号**；并澄清 `tdx_parser.py` 本身保证同谱系内 id 稳定。）

## 现象

用 `C:\Users\sunck\home\projects\tdx_project\tdx.db` 当差分基线，跑出的差异统计是：
daily 改写 **12,317,241** 行 / 新增 1,690,944 行 / 基线独有 1,582,957 行。
两库明明是同一批数据（同为 3611 只、同日期范围 19900102~20260828），差异却几乎等于全库。

## 根因

生成器按 `file` 关联两库，而 `file → meta_id` 依赖「该库 `meta.id` 与数据表 `meta_id` 同号」这一前提。

注意：**这不是「id 会变」的问题**。`tdx_parser.py:673-680` 本身保证同谱系内 id 稳定
（按 `file` 命中就复用 `exist_meta[file]['id']`，只有新文件才取 `next_id`；`--rebuild` 也复用同一套）。
问题出在那份库**内部 meta 与数据表被编成了两套号**：

实测 `C:\Users\sunck\home\projects\tdx_project\tdx.db`：
- 它的**数据表**与当前主库是同一套 id 空间：按 `(meta_id, date)` 对齐后，14,008,185 行日线**值差异 = 0**；
- 但它的 **`meta` 表被重新编号** 为连续 `1..3611`，而数据表是 `3..3637`（含 24 个空洞）；
- 于是内部错位：茅台在该库 `meta` 里是 `id=732`，茅台的真值却落在 `daily.meta_id=756`
  （`daily[732]` 是别人的 5341 行、起始 20040524，而茅台是 5993 行、起始 20010827）。

## 现在的规避方式

出包前先跑 `check_meta_consistency`：核对 `meta` 行数、悬空 `meta_id` 行数、`first_date`/`last_date` 是否与数据相符，
**任一库不自洽就立刻停住**（`exit 3`），不进差异扫描、不产包，并提示改用「设备已同步版本主库的整份拷贝」当基线。

正确基线已存档：`C:\Users\sunck\home\tdx_baseline.db`。
