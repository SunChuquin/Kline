# 活跃事务内 `DETACH` 必失败（SQLITE_LOCKED）（2026-09-23）

## 现象

设计「会话式单事务落主库」（一个事务跨多个 HTTP 请求）时，原计划每个补丁分片走
`ATTACH` → 写五张表 → `DETACH`。实测 **`DETACH` 必然失败**：

```
SQLITE_LOCKED: database bkt is locked
```

且**与是否读过该片无关** —— 只要事务还活着，就 `DETACH` 不掉。只有 `COMMIT` 之后才能 `DETACH`。

## 根因

`ATTACH`/`DETACH` 与事务的交互约束：在一个活跃的写事务内，已 `ATTACH` 的数据库无法被分离
（分离需要拿到该库的写锁，而锁正被当前事务持有）。

## 现在的规避方式

**不 DETACH** —— 每片用**唯一别名**保持挂载，会话结束随连接关闭隐式释放：

```
begin   : BEGIN IMMEDIATE
apply s0: ATTACH 's0.db' AS bkt0 → 写五张表 → （不 DETACH）
apply s1: ATTACH 's1.db' AS bkt1 → 写五张表 → （不 DETACH）
commit  : UPDATE meta.last_date（用累积的 temp.patch_file_max）→ COMMIT → sqlite3_close
```

- 末日累积：`apply` 时把该片的 `MAX(date)` 写进 `temp.patch_file_max`，`commit` 用它更新 `meta.last_date`
  （这样就不需要在 COMMIT 前重新 `ATTACH` 各片去取 max）
- **硬上限**：`SQLITE_MAX_ATTACHED = 10`（含主库自己占 1）→ **分片数 N 必须 ≤ 6**
  （编排器已在参数层校验：`--shards 7` 直接报错）
- 功能等价、**原子性不变**（仍是一个事务）
