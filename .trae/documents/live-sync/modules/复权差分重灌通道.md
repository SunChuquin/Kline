# 复权差分重灌通道（PC 侧）

## 1. 它是什么 / 在哪

**一句话职责**：主库存的是**前复权**K线，而前复权因子会因除权除息而变化、从而改写历史；
本通道把「被改写的历史行」以最小差分包推给设备，避免整库替换（1.38GB、2 分钟、要重启）。

| 文件 | 角色 |
| :--- | :--- |
| `Kline/src/tdx_parser.py` | 通达信导出 txt → `tdx.db`；新增 `--rebuild` 全量重读模式 |
| `c:\Users\sunck\home\projects\ios\TrollRestore\diff_live_patch.py` | 新库 vs 基线 → `patch_<seq>.db` |
| `TrollRestore/push_bucket_usb.py` | PUT 沙盒 → `POST /sync/merge-bucket` |
| `Kline/Data/LiveDataStore.swift` `mergeBucket` | 设备侧合并（**对包内日期不做任何校验**，所以零改动支持任意历史日期） |

## 2. 为什么需要它（复权语义）

从 `[P0]` 起读；这条链解释了为什么「只同步最新一根」不够。

```mermaid
flowchart LR
    P0[某标的除权除息] --> P1[前复权因子变化]
    P1 --> P2[该标的全部历史价格<br/>被重新缩放]
    P2 --> P3[只追加当天一根<br/>不够]
    P3 --> P4[必须整段重灌历史]
```

**图里没画出来的部分**：
- 因子来源是通达信 gbbq（股本变迁）文件；本机实测常态 **22~24 只/交易日**发生除权除息，分红季峰值上百只。
- 前复权是**以最新价为基准往前调整**，所以一次新除权会让该标的**回填到上市首日**的全部价格变化——这正是「整段重灌」而非「补几根」的原因。
- 不复权的原始价在 `C:\new_tdx64\vipdoc\...\*.day` 里，与库内前复权价截然不同（库里 `close < 0` 的行有 719,198 行，原始 `.day` 同日期是正常正数）。

## 3. 三步流程

从 `[X1]` 起读；`X2` 之后的输入是**新的 tdx.db**，不是 txt。

```mermaid
flowchart LR
    X1[通达信客户端<br/>补数据/导出 txt] --> X2[tdx_parser --rebuild<br/>重建 tdx.db]
    X2 --> X3[diff_live_patch<br/>对比基线]
    X3 --> X4[push_bucket_usb<br/>推补丁]
    X4 --> X5[设备合并<br/>+ 热刷新]
```

**图里没画出来的部分**：
- 第一步是**用户手动**动作，本链路不负责补缺口算法。
- `X2` 必须让**变过的文件整文件重读**（`--prev-dir`，或退一步用 `--rebuild`），否则复权改写的历史行会被永久漏掉——见 §6 那条陷阱。
- `X3` 前必须先有**自洽的基线库**（整库拷贝），本机已存档 `C:\Users\sunck\home\tdx_baseline.db`。

命令（**推荐路径**：不重建任何库，直接由「新 txt + 基线库」出差分）。整流程实测 **57.8s**（见 §9）：

```powershell
# ① 出包：直接比对新 txt 与基线库（不重建 tdx.db）
python src/txt_patch_builder.py --old-txt-dir C:\Users\sunck\home\tdx_data_old `
       --new-txt-dir C:\Users\sunck\home\tdx_data --seq 6

# ② 推送并应用到设备主库（PUT → apply-patch → 清增量库 → reload）
python TrollRestore/push_bucket_usb.py <产出目录>\patch_6.db --apply-main

# ③ 可选（不计入 60s 预算）：把同一补丁应用到 PC 本地基线，避免下一轮重复计算已同步差异
python TrollRestore/apply_patch_local.py --patch <产出目录>\patch_6.db --yes
```

**为什么 ② 要清增量库**：App 查询规则是「同一 date **以增量库为准**」，而增量库里可能残留旧值
（旧补丁推入的旧历史、东财快照的**原始价**），会**遮蔽**刚写进主库的新值。主库更新后已含全部数据，
故清掉安全且必要（增量库缺失时 App 正常、全部走主库）。

旧路径（保留可用，但**本流程不再调用**）：先 `tdx_parser --prev-dir` 重建 `tdx.db` 再跑 `diff_live_patch.py`。
实测那条路要 **585.1s**（`--prev-dir` 下文件全算变更 → 整文件重读 + 全历史 UPSERT ≈ 2300 万行写入）。

## 4. 差分包契约

表结构与**分片完全一致**（复用生成端的 `build_bucket_file`），因此设备侧合并逻辑原样可用：

```sql
bkt_meta(file TEXT PRIMARY KEY, code TEXT, name TEXT, type TEXT, updated_at INTEGER)
bkt_daily / bkt_weekly / bkt_monthly(file TEXT, date INTEGER, open, high, low, close, vol, amo,
                                     PRIMARY KEY(file, date))
```

与分片的唯一差别（也是它存在的理由）：

| 维度 | 分片 `bucket_<id>.db` | 补丁 `patch_<seq>.db` |
| :--- | :--- | :--- |
| 覆盖日期 | 一片 = 一个交易日 | **任意多日期，可跨 36 年** |
| 数量约束 | 受 `KEEP_BUCKETS = 30` 滚动约束 | **不受约束**；「最近 N 个」只作用于幂等记录长度 |
| 谁产出 | 生成端（云端/PC 分片生产者） | PC 差分生成器 |
| 合并入口 | 同一个 `LiveDataStore.mergeBucket` | 同一个 |

manifest 增加 `patches: [TdxLiveBucket]?`（Optional，旧 manifest 向后兼容），设备侧按 sha256 幂等去重。

- [[20260922-行情同步-差分包不受KEEP_BUCKETS约束]] — 分片契约装不下跨年历史

## 6. 已知陷阱

- [[20260922-last_size增量永久漏掉复权改写的历史行]] — 不修这个，差分基准本身就是错的
- [[20260922-基线库meta与数据表id空间不一致产千万行假差异]] — 换基线前先跑自洽性校验
- [[20260923-活跃事务内DETACH必失败]] — 会话式单事务不能逐片 DETACH；改用唯一别名 + 上限 N≤6
- [[20260923-本机HTTP代理导致本地下载假503]] — 访问本地 5051 必须全局绕代理
- [[20260923-行情同步-五张周期表全路径一致性]] — 季/年线在三条路径上都要最新；裁剪要周期感知
- [[20260922-全表JOIN逐行随机探查比逐文件慢10倍]] — 差异扫描必须逐文件；实测「每文件固定开销」可忽略，批处理无效
- 差分生成器**按 `file` 关联**（不用 `meta_id`）：`file` 是端到端契约键（设备增量库、分片、补丁全用它），唯一且带市场前缀；
  `code` 不能用（主库有 55 处重复）。`meta_id` 在同谱系内其实是稳定可比的（见 [[20260922-行情同步-关联键用file而非meta_id]]），
  但它只是 parser 的记账细节，且实测存在「库内 meta 与数据表不同号」的脏库 → 不采用
- 浮点比对必须带容差（用 `1e-6`）：直接 `!=` 会因 INT/REAL 表示噪声（`10` vs `10.0`）产生海量假差异；容差过大又会漏掉真实复权改写
- `quarterly` / `yearly` 只统计**不入包**（契约里没有 `bkt_quarterly` / `bkt_yearly`）；基线缺这两张表要能优雅跳过
- 基线里独有的 `(file, date)` **只统计不删**：多为退市标的的尾部历史，删掉会让设备失去「已退市但仍持有」的K线

## 7. 亮点 / 可复用的做法

- **每次跑完复核两库未被修改**：只读打开（`mode=ro` + `PRAGMA query_only=1`）+ 跑完比对 sha256/mtime/size，把「读数据」变成可验证的硬约束。
- **拒绝而不是绕过**：基线不自洽时直接 `exit 3` 不产包，并给出「改用整库拷贝当基线」的可操作提示。假差异被推给设备比失败更糟。
- **输出可复查清单**：每次出包同时落盘「受影响 file 清单 txt」（file / 序号 / bytes / rows / sha256），可直接作为 manifest `patches` 的素材。
- **无差异不产空包**，明确打印「无差异」并正常退出（exit 0），便于放进自动化。

## 9. 性能（实测，1.4GB 库对）

### 9.1 端到端（2026-09-23 真机，**推荐路径**）

| 阶段 | 实测 | 备注 |
| :--- | ---: | :--- |
| PC 出包（`txt_patch_builder`） | **25.4s** | A 11.4 / B 8.9 / C 5.1 → 843,767 行 / 76.3 MB |
| usbmux forward 建立 | 4.1s | 固定开销 |
| PUT 76.3 MB | 5.9s | 12.92 MB/s |
| **设备端 apply-patch（主库 UPSERT）** | **21.5s** | 84 万行；加 pragma 前 27.9s |
| 清增量库 + reload | 0.5s | |
| **合计** | **57.8s** | **< 60s**（余量约 2s，偏紧） |

设备端 APPLY 是最大单项（37%）。它慢是因为 iPad mini 4 上要把 84 万行 `INSERT OR REPLACE`
进一个 1400 万行、带 `(meta_id,date)` 主键索引的库；主库连接上**原本一个 pragma 都没设**，
加了会话级 `cache_size=-32768` / `temp_store=MEMORY` / `synchronous=NORMAL` 后 27.9s → 21.5s。

### 9.2 旧路径（先重建 PC 库再差分）—— 已不推荐

`tdx_parser --prev-dir` 实测 **585.1s**（3641 个文件全算变更 → 整文件重读 + 全历史 UPSERT ≈ 2300 万行）。

### 9.3 差分扫描的三层优化（历史，仍适用于 `diff_live_patch.py`）

从 400.0s 降到 7.0s（约 57×）：

| 层 | 动作 | 效果 |
| :--- | :--- | :--- |
| ① 扫描形状 | 全表大 JOIN → **逐 file 局部核对** | 386.7s → 110.5s。见 [[20260922-全表JOIN逐行随机探查比逐文件慢10倍]] |
| ② 变更裁剪 | 只比「txt 真变过的标的」 | 110.5s → 0.0s（0 候选）/ 个位数秒（20~30 只） |
| ③ 固定开销 | 自洽性检查收窄到候选范围；`sha256` 改按需 | 100.2s → < 10s |

### 9.4 `txt_patch_builder` 的性能红线（**三条，都能把耗时抬高数倍**）

- 分类与解析**融合**，每文件**只开 2 次句柄**（旧 1、新 1）→ A 段 23.6s → 15.0s → 11.4s
- **周一映射必须缓存**（每行构造 `datetime` 会让 B 段从 10s 涨到 20s）
- append 文件的周/月只查基线**最后 8 行**（`ORDER BY date DESC LIMIT 8`），否则 3440 只 × ~1200 行白取，B 段多花约 50s
- **取「基线当期 bar」必须用批量查询**：4 条 `WHERE date BETWEEN <周期日历起止>`（各 3611 行、共 14,444 行、约 1.3s）；
  若写成逐标 `WHERE meta_id=? AND date BETWEEN ? AND ?`（3611 × 4 ≈ 14,444 次随机探查）→ **A 段 9.5s 抬到 59.8s**
- `MAX(date) FROM daily`（全表 14M 行扫）改 `MAX(meta.last_date)`（3611 行）→ 冷缓存下省 >2s

### 9.5 并行出包与流水线（2026-09-23 新增，**含被实测推翻的预期**）

`txt_patch_builder.py --shards N --workers W`：把标的按 file 稳定分组（排序后 `index % N`，两两不交、并集为全集），
**每个 worker 独立完成自己那份的 A+B+C 并写自己的补丁文件**（`patch_<seq>_s<i>.db`；`multiprocessing`）。
**共享工作必须上提到父进程**（`idmap`/`meta_src`/`dmax·LO`/`CUR_BAR`，下发约 1.15 MB）——
否则每个 worker 各做一遍 `CUR_BAR`（4 条周期表全表扫 ≈ 1s/份）。

| 方式 | PC 出包耗时 |
| :--- | ---: |
| 单包（1 进程） | 20.8~24.4s（热/冷） |
| **4 片 / 4 worker（并行）** | **9.7~13.7s**（约 2×） |

正确性硬门槛（已验）：**各片行数之和 = 单包**（逐表五张全等）、**并集 = 待处理标的数、两两交集 = 0**、
`--self-check` 0 不一致、`--only-shard i` 与整跑第 i 片**字节相同**。

`TrollRestore/sync_pipeline.py`（编排器）：一次 `forward()` 全程保持（与首批出包**并发启动**）、
分片产出即 **PUT + apply**（`patch-session/apply`，与 PC 后续分片重叠）、全部成功后**一次** `commit`、
最后清增量库 + reload 各一次；失败则 `rollback` 且**不清库**。

**端到端实测（真机 v1.0.2 (380~383)）**：

| 方案 | 端到端 | PC 出包 | 设备 PUT | 设备 APPLY | commit |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 串行基线（单包，仅日/周/月） | **57.8s** | 25.4 | 5.9 | 21.5 | （含在内） |
| 流水线 N=4/W=4 | 47.3s | 35.3 | 5.7 | 17.9 | 12s |
| 流水线 N=2/W=2（修 commit 前） | 43.8s | 13.3 | 5.2 | 12.7 | 12s |
| **流水线 N=2/W=2（修 commit 后，热）** | **32.7s** | 14.7 | 6.2 | 8.1 | **0.7s** |

**修掉那 12s 的关键**：真凶是 **SQLite 默认 `wal_autocheckpoint=1000页` 在 COMMIT 语句内部**
对累积的 **214.6 MB WAL** 做全量回写。会话连接设 `PRAGMA wal_autocheckpoint=0` 后
**COMMIT 13,829ms → 633ms**；回写改为**响应之后**用独立短连接做 `wal_checkpoint(PASSIVE)`
（WAL 语义下 App 立刻能读到已提交数据 —— 已用「临时改值 → App 侧 0.9s 读回新值」决定性验证）。
详见 [[20260923-wal_autocheckpoint在COMMIT内吃掉十几秒]]。

**结论：端到端 57.8s → 32.7s（1.77×）**（冷缓存会到 38~56s，波动主要来自 PC 出包与设备 I/O）。
剩余构成：PC 出包 ~15s + 设备 PUT ~6s + 设备 APPLY ~8s，两者只重叠了一部分；
**设备端仍是单写者下界**，继续加并行度没有意义。

### 9.6 两个反直觉的实测结论（别凭直觉优化）

- **`UPDATE ... FROM` + `INSERT ... WHERE NOT EXISTS` 比 `INSERT OR REPLACE` 慢 66%**
  （中位 7.998s vs 4.825s，同副本 `BEGIN…ROLLBACK` ×5 取中位）。
  直觉是「REPLACE 先删后插 = 双倍索引开销，所以 UPDATE 更快」，**实测相反** →
  设备端 APPLY 保持 `INSERT OR REPLACE`，**接受 21.5s 作为下界**。
- **下载设备文件返回的 503 不是服务器发的**（服务器代码只有 200/400/404/500），
  而是本机 `HTTP_PROXY` 把回环地址也走代理造成的假象 → 见 [[20260923-本机HTTP代理导致本地下载假503]]。

## 10. 遗留 / 未验证

- [ ] `--rebuild` 是否真的修掉了复权改写漏读
  - **怎么验**：同一份 txt 先增量跑一次、再 `--rebuild` 跑一次，比对某已除权标的的历史价格（增量模式应不一致）
  - **谁来验**：用户（在其通达信客户端全量更新时一并做），因为会改写主库
- [ ] 真实一次差分（而非合成用例）的包体积与耗时
  - **怎么验**：用户补完缺口后跑一次 `diff_live_patch.py`，看输出的「包体积 / 总耗时」
  - **谁来验**：用户（需要有真实的新库）
- [ ] 补丁的云端分发路径（manifest `patches`）尚未走过一次真实下载
  - **怎么验**：把 `patches` 写进 manifest 放到可访问源，让设备走一次拉取；目前只验证了 USB 直推
  - **谁来验**：AI 可自验（构造 manifest + 本地 HTTP 源），但**当前无云端源可用**（见 [[20260922-境外Actions访问国内行情源被502拒绝]]）
