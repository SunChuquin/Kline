# 五张周期表在「所有」更新路径上都要最新（2026-09-23）

## 决策

主库的五张周期表 `daily` / `weekly` / `monthly` / `quarterly` / `yearly`，
**在三条更新路径上都必须反映最新数据**，且**增量库也发布这五张表**（查询层统一「live 覆盖 main」）。

| 路径 | 做法 |
| :--- | :--- |
| 差分升级（补丁） | 补丁携带 `bkt_quarterly` / `bkt_yearly`，PC 端用基线算出正确的当期 bar |
| 每日定时（东财直连） | 把当期季/年 bar 写进**增量库**（用「主库当期 bar ⊕ 新日线」合并） |
| 全量重建（`tdx_parser`） | 本就产出五张表 → **只需验证，不改代码** |

## 为什么（根因）

**遗漏实证**：主库 `quarterly` 238,879 行 `MAX(date)=20260806`、`yearly` 62,334 行 `MAX(date)=20260806`，
而 `daily`/`weekly` 已到 `20260828`。App 的季/年线视图**回落读主库**，所以视图里最后一根季线还停在 `20260701`。

**原设计的前提不成立**。`LiveDataStore` 原先明确不发布季/年线，注释理由是「季/年线无法被有限窗口完整覆盖」
（`LiveDataStore.swift:19`）。但三条证据表明这个理由站不住：

1. 生产端（PC 分片生成器 / 设备侧每日路径）**都能拿到基线/主库** —— 有限窗口的限制**只存在于「只有增量库」的视角**，
   一旦允许读主库，就能算出正确的完整周期 bar。
2. `_trimLocked` 原先只裁剪 `["daily","weekly","monthly"]` 三张表 —— 说明季/年线不发布**不是**存储模型的必然。
3. 季/年线的「当期」bar 本来就应该跟着当日数据更新（通达信本身也是这样显示的）。

## 关键实现约束（踩过才知道）

- **聚合一律用「增量合并」，不得整周期重算**：开局一次性由基线最大交易日推出当期四个周期，
  每只标的只对**被新数据触及的周期**取基线那一根 bar，与新日线合并
  （`open` 取周期首行、`high/low` 取极值、`close` 取末行、`vol/amo` 累加）。
  **只有 `rewrite`（除权改写）才整只标的全量重算**。
- **取基线 bar 必须用批量查询，不能逐标查询**：4 条 `WHERE date BETWEEN <周期日历起止>` 的整表范围查询
  （各命中 3611 行、共 14,444 行、约 1.3s）即可拿到所有标的的当期 bar。
  若写成逐标 `WHERE meta_id=? AND date BETWEEN ? AND ?`，3611 × 4 ≈ 14,444 次随机探查会把出包 A 段
  **从 9.5s 抬到 59.8s**。
- **裁剪必须「周期感知」**：季/年线 bar 的 `date` = 该周期**首个交易日**（如季线 `20260701`），
  远早于「最近 N 个交易日」。若沿用日/周/月的 `date <= beforeDate` 规则，**当期 bar 会被误删**；
  若完全不裁，旧周期 bar 会累积并在后续主库更新后**遮蔽**主库的正确值。
  故季/年线只保留 `date >= 当期日历起始`。
- **分片契约不变**：`bucket_<id>.db` 仍只有日/周/月 —— 增量库发布五张表是**设备侧**的事，
  PC 分片生成器的契约不动（`build_bucket_file` 的 `periods` 参数默认值保持三张表）。
- **老增量库要有迁移兜底**：`_ensureWritableSchemaLocked` 必须**幂等执行 schemaSQL**，
  否则老库（有 `live_meta`、缺 `live_quarterly`）写入会因缺表整体回滚。
