# 补丁按行 UPSERT 进主库，不替换整个 tdx.db（2026-09-23）

## 决策

设备侧新增 `POST /sync/apply-patch`：把补丁包的行用**一条集合式 SQL** 按主键 UPSERT 进主库 `tdx.db`，
**不替换整个文件、不需要重启 App、不经过增量库中转**。

```sql
INSERT OR REPLACE INTO <daily|weekly|monthly|quarterly|yearly>(meta_id,date,open,high,low,close,vol,amo)
SELECT m.id, b.date, b.open, b.high, b.low, b.close, b.vol, b.amo
FROM bkt.bkt_<表> b JOIN main.meta m ON m.file = b.file;
```

### 多分片主机制：会话式单事务（`patch-session`）

单包走 `POST /sync/apply-patch`（一条集合式 SQL 一次写五张表）；**多分片是现在的主机制**，
改走会话端点，把多片合并进**同一个事务**，避免每片各开一次事务 / 各清一次增量库：

| 端点 | 作用 |
| :--- | :--- |
| `POST /sync/patch-session/begin` | 开独立连接 + `BEGIN IMMEDIATE`，置 `PRAGMA wal_autocheckpoint=0`，启动 120s 看门狗 |
| `POST /sync/patch-session/apply?name=<片>` | 在会话连接上 `ATTACH` 该片 + 写五张表 + `DETACH` |
| `POST /sync/patch-session/commit` | `UPDATE meta.last_date`（MAX 防回退）+ `COMMIT` + 关连接 |
| `POST /sync/patch-session/rollback` | `ROLLBACK` + 关连接（丢弃已喂入的片、释放写锁） |

会话连接在 `begin` 置 `PRAGMA wal_autocheckpoint=0`：否则 `COMMIT` 语句内部会对累积的 ~215MB WAL
做**全量回写**，把一次 COMMIT 拖到 **12s**；关掉后 **COMMIT 13,829ms → 633ms**（端到端 commit 12s → 0.7s）。
回写改为**响应发出后**用独立短连接做**有界延迟** `wal_checkpoint(PASSIVE)`（随后 `TRUNCATE` 真截断），
不阻塞 App 的 `dbQueue`；WAL 语义下已提交数据对其它连接立即可见，故此处只做空间回收、与正确性无关。
详见 [[20260923-wal_autocheckpoint在COMMIT内吃掉十几秒]]、[[20260923-活跃事务内DETACH必失败]]。

## 为什么（根因）

1. **整库替换的代价**：主库 1.4 GB，走 `/upload` 流式约 2 分钟，且**必须重启 App**
   （主库是「启动时打开」语义）。而本次差分只有 78.1 MB / 86 万行。
2. **只有差异需要落地**：差分已经把「该改哪些行」算得很准（863,627 行 = 全库 1400 万行的 **6.2%**），
   没有理由为了改 6% 而重写 100%。
3. **集合式 SQL 而非逐行 bind**：86 万行若在 Swift 里逐行 `sqlite3_bind_*`，光绑定开销就很可观；
   一条 `INSERT ... SELECT ... JOIN` 把映射（`file → meta_id`）与写入都交给 SQLite 执行器。
   - 顺带：`MainDBMerger`（App 内手点路径）是逐行 bind 的，所以**没有复用它**，但也没有改动它。

## 代价 / 现在的规避方式

- **实测 21.5s**（86 万行）——这是整条 57.8s 流程里最大的单项（37%）。
  优化：主库连接上原本**一个 pragma 都没设**，加了会话级
  `cache_size=-32768` / `temp_store=MEMORY` / `synchronous=NORMAL` 后 27.9s → 21.5s（−23%）。
  这些 pragma 都用 `defer` 还原，不影响其它读写路径。
- **必须清增量库**：App 查询规则是「同一 date **以增量库为准**」，而增量库可能残留旧值
  （旧补丁推入的旧历史、东财快照的**原始价**），会**遮蔽**刚写进主库的新值。
  主库更新后已含全部数据，故清掉安全（增量库缺失时 App 正常、全部走主库）。
- **`meta.last_date` 必须防回退**：最初的写法 `SET last_date = (SELECT MAX(...))` 在补丁只含**旧日期**时
  会让 `last_date` **回退**（实跑复现 20260902→20260828），进而使下一轮「按缺口取片」重复下载 →
  已改成 `MAX(COALESCE(last_date,0), COALESCE((SELECT MAX(...)),0))`。
- **主库无此标的的 file 会被 JOIN 丢弃**：这是预期行为（要进得先插 `meta` 行），响应里用 `skippedFiles` 显式报出。
