# 变更判定用「新旧两份 txt 目录」，不在库里存状态（2026-09-22）

## 决策

「哪些标的真变了」的判定输入 = **新旧两份 txt 目录**（用户保证每次增量更新时都存在），
判定逻辑集中在 `Kline/src/txt_changes.py` **唯一一份实现**，被 `tdx_parser.py` 与 `diff_live_patch.py` 共同 import。
**不新增库内状态表，也不写 sidecar JSON。**

## 为什么（根因）

先算清了账：差分的耗时地板是「把所有 1400 万行都比一遍」（实测 daily 单周期 208s，全跑 386.7s）。
要再快只能**少比一些文件**，也就是必须知道「哪些文件的 txt 内容变了」。

备选方案与取舍：

| 方案 | 问题 |
| :--- | :--- |
| 在 `tdx.db` 里加 `import_state` 表存 txt 指纹 | 状态必须**与基线严格同步**：基线一换就失效；且一旦出现「状态陈旧」，会**静默漏判**（以为没变→不比→设备拿不到复权修正）。风险高，坑深。 |
| 写 sidecar JSON 存指纹 | 同上，还多一个「文件与库不同步」的失效面 |
| **用新旧两份 txt 目录对比**（采纳） | 无需任何存储；目录本身就是状态的真相源；错了也只会「多比一些文件」（退化到全量），**不会静默漏判** |

关键性质：**失败方向是安全的**。旧目录若因复制丢了 mtime，结果是「全部文件都算变更」→ 退化到全量比对（慢但正确），而不是漏判。

## 代价 / 现在的规避方式

三种比较档位（`--txt-compare`，实测 3637 文件 / 701MB×2）：

| mode | 依据 | 实测 | 说明 |
| :--- | :--- | ---: | :--- |
| `stat`（默认） | `(size, st_mtime_ns)` | **0.1s** | 只 stat 不读内容。实测能抓到「同尺寸改写」（改写会更新 mtime） |
| `content` | Python sha256（1MB 分块） | ~30s | 纯内容比对，无外部依赖 |
| `bc` | Beyond Compare 5 CLI（`criteria crc`） | 27~30s | 见 [[20260922-BC默认按时间戳判差异会漏同尺寸改写]] |

- 瓶颈不是哈希也不是磁盘（磁盘顺序读实测 340MB/s），而是**3637 个文件的逐文件打开 + 杀软扫描开销**——
  所以 `stat` 与 `content` 差两个数量级，而 `content` 与 `bc` 几乎一样快。
- 两个脚本共用同一判定，避免「导入认为变了、差分认为没变」这类两套实现漂移。
- **导入端与差分端的口径必须一致**：`tdx_parser.py --prev-dir` 判定为「变更」的文件会被**整文件重读**
  （不能只读尾巴——复权改写常让价格缩放而字符数不变，只读尾巴会永久漏掉历史行），
  差分端对同一集合做行级比对。判定不一致就会出现「库更新了但没进包」或反之。
