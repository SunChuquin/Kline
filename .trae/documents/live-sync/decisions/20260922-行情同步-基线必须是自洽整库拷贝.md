# 差分基线必须是「自洽的整库拷贝」（2026-09-22）

## 决策

差分用的基线库，必须是**一份完整、自洽的主库拷贝**（即设备已同步过的那一版 `tdx.db` 原样复制），
不能随便拿另一个同规模的库顶上。生成器内置自洽性校验，不通过就 `exit 3` 拒绝出包。

## 为什么（根因）

**前提澄清（2026-09-22 经用户指出后修订）**：`tdx_parser.py` **本身就保证 id 在同一条库谱系里稳定**——
它按 `file` 查已有 `meta`，命中就复用 `exist_meta[file]['id']`，只有真正的新文件才取 `next_id`
（`tdx_parser.py:673-680`，且 `exist_meta` 以 `file` 为键，见 `:662`）。所以同一份 parser 反复增量或 `--rebuild`
出来的库，`meta_id` 是可比的。**「id 会变」不是本决策的理由。**

真正的理由有两条：

1. **跨谱系不可比**：不同来源/不同版本的库，id 分配可以完全不同。
2. **更隐蔽的一种：同一个库文件内部就可能 `meta` 与数据表不同号。** 实测 `C:\Users\sunck\home\projects\tdx_project\tdx.db`：
   - 它的**数据表**与当前主库是**同一套 id 空间**——按 `(meta_id, date)` 对齐后，**14,008,185 行日线的值差异 = 0**，
     说明数据就是同一份；
   - 但它的 **`meta` 表被重新编号过**：连续 `1..3611`，而数据表是 `3..3637`（含 24 个空洞），
     于是内部错位——茅台在该库 `meta` 里是 `id=732`，而茅台的真值落在 `daily.meta_id=756`。
   - 结果：按 `file` 关联会把茅台的历史配到别人身上 → **1231 万行假差异**，比不合并还糟。

所以基线的要求准确说是：**与当前库同谱系、且内部自洽**（`meta.id` 与数据表 `meta_id` 同号）。

## 代价 / 现在的规避方式

- 代价：多占一份 1.38GB 磁盘。本机已存档 `C:\Users\sunck\home\tdx_baseline.db`（就是当前 `tdx.db` 的整份拷贝）。
- 规避：`check_meta_consistency` 只用 `daily` 做判据（`meta` 行数 / 悬空 `meta_id` 行数 / `first_date`·`last_date` 是否与数据相符），
  任一库不自洽就立刻停住，**绝不进入下面的差异扫描**。另留 `--allow-inconsistent-db` 供确知库就是这样时才用（结果不可信）。
- 基线维护节奏：每次重建 `tdx.db` 出完补丁后，把新库拷成新基线（或保留旧基线只做一次性对比，按需选择）。
