# 行情同步的日志与排障

本模块**没有独立的指标 / 埋点体系**，排障靠五组日志前缀 + 一族 HTTP 端点。这不是缺陷——
同步结果本身就是可观测的（库内行数与最新日期一查即知），没必要再加一层。

## 日志前缀（都在 `Documents/debug_log.txt`）

| 前缀 | 来源 | 看什么 |
| :--- | :--- | :--- |
| `[WatchlistSync]` | `WatchlistSyncManager` | 一次清单同步的完整链路：并集 N 只 → 命中 M 只 → 跳过 K 只（含样例原因）→ 交易日 → 写入结果 |
| `[EMQuote]` | `EastmoneyQuoteFetcher` | 覆盖表载入条数 / 批失败 / 交易日不一致 / 完成统计 |
| `[TdxSync]` | `TdxSyncManager` | 调度启动、时刻表迁移、manifest 与分片下载、补丁合并 |
| `[Live]` | `LiveDataStore` | 重载完成（前后行数、最新日期、耗时、指纹）、指纹未变跳过热重载 |
| `[Patch]` | `KlineHTTPServer`（apply-patch / `PatchSessionManager` / 延迟回写） | 补丁应用进主库成功·失败、`会话 begin/apply/commit/rollback`、`commit 分解`（队列排队/UPDATE meta/COMMIT/sqlite3_close）、`延迟回写 第N次 log/checkpointed/rc/busy`、主库读回探针 |
| `[DB] dataVersion → n` | `DatabaseManager` | **判断「该不该刷新」看这里**：内容没变时不应出现 |
| `[Cache] dataVersion 变化 → 重取行 n=` | `MarketRowCache` | 刷新后受影响的行数 |

## HTTP 端点（端口 5051，需 App 前台未锁屏）

- `GET /sync/status` → `available` / `metaCount` / `dailyCount` / `latestDate` / `earliestDate` / `reloadCount` / `fingerprint` / `path`
  - **最快的健康检查**：`dailyCount` 与 `earliestDate` 的变化直接反映写入是否生效。
- `POST /sync/merge-bucket?name=...&sha256=...` → 合并分片/补丁**进增量库**，返回 `合并完成 meta=… daily=… weekly=… monthly=… quarterly=… yearly=… 覆盖=…只`
  - 设备侧合并耗时就在这条的响应时间上（实测 576KB→0.1s，22.5MB/25 万行→1.3s）。
- `POST /sync/apply-patch?name=...&sha256=...` → 补丁**按行 UPSERT 进主库 `tdx.db`**（不经增量库、不重启，单事务）。
  文件需先 `PUT /sandbox/live/`。响应含 `日/周/月/季/年` 各自写入行数、覆盖只数、`skippedFiles`（主库无此 file）。
- 会话式（跨请求单事务，多分片时用）：
  - `POST /sync/patch-session/begin` → 开独立连接 + `BEGIN IMMEDIATE`（含 `wal_autocheckpoint=0`）
  - `POST /sync/patch-session/apply?name=<片>` → ATTACH 该片 + 写五张表（**不 DETACH**，别名保持到会话结束）
  - `POST /sync/patch-session/commit` → `UPDATE meta.last_date`（MAX 防回退）+ `COMMIT` + 关连接；**响应后**异步延迟回写 WAL
  - `POST /sync/patch-session/rollback` → `ROLLBACK` + 关连接（释放写锁，已喂入的片全部丢弃）
  - **失败行为**：任一步失败即回滚，编排器（`sync_pipeline.py`）**不清增量库**；成功才清。
- `GET /sync/probe?file=SH%23600519` → 在 **App 自身连接**上只读读回该标的的日线末日 / 最新季线 bar（核对用，验证 WAL 未回写时 App 也读得到新值）。

> ⚠️ **延迟回写**：会话 `commit` 后主库 WAL 停留在几百 MB，需后台 `wal_checkpoint` 回写（约 13~120s）才落进 `tdx.db` 文件。
> **按文件拉 `tdx.db` 的工具（`verify_main_db.py`）必须等回写完成再拉**，否则拿到的是 WAL 里的旧数据（App 不受影响，App 读 WAL）。

## 排障路径（按顺序）

1. `GET /sync/status` 通不通 —— 不通说明 App 不在前台或 USB 未连接，**先解决这个**再看别的。
2. `dailyCount` / `latestDate` 有没有动 —— 没动看 `[WatchlistSync]` 与 `[EMQuote]`：是并集为空？映射不到？还是接口没数据？
3. 数据进去了但界面没变 —— 看 `[Live]` 指纹是否变化、`[DB] dataVersion` 是否自增、`[Cache]` 是否重取。
   若「指纹时间戳变化但内容一致（sha256 未变）→ 跳过热重载」，说明这次写入的数据与库里相同（正常行为）。
4. 想确认合并内容是否真的对 —— 下载设备 `tdx_live.db` 与 PC 主库逐行比对（本次实测 `27#HSI` 等值不一致 = 0）。

拉日志：`python TrollRestore/deploy_kline_to_ipad.py --pull-logs`

## 不做什么

- 不加打点上报（数据本身可查，且设备无外网依赖时打点也会失败）。
- 不为「写前判定被跳过」单独加日志级别——`upsertDaily` 的返回 `message` 已写明「无变化…跳过写入」。
