## 1. 一句话原理

设备上**不动**原来那个 1GB+ 的整库 `Documents/tdx.db`（全市场历史，也可用「合并到 tdx.db」把增量写回，见 §7），
另外维护一个**增量库** `Documents/tdx_live.db`：装**全市场约 3611 只**标的最近窗口内的日/周/月线
（季/年线不再发布——有限窗口聚合会得到"部分周期"，语义是错的）。

云端把增量按**14 个自然日一片**切成 `bucket_<id>.db`（最多保留 10 片 ≈ 5 个月）；App 只下载**与自己缺口相交**的那 1~2 片。

App 查询时按 **「同一 date 以增量库为准，其余由主库补齐」** 合并两个库，所以：

- 行情列表、自选、K线图、条件单/预警**上层代码零改动**就能看到新数据（含自选之外的任意标的）；
- 增量库文件一变，App **自动热刷新**（指纹变化 → 重载 → 广播数据版本），**不需要杀进程重启**。

体积实测（2026-09-22）：单根K线约 111 字节 → 全市场 × 14 天窗口 ≈ **5MB/片**（未压缩）；典型每次只需 1~2 片。
`POST /sync/reload` 后设备侧立即变为 `available=true / 覆盖 N 只 / 区间 起~止`。

## 2. 三通道怎么选

| 通道 | 何时用 | 需要电脑开机 | 需要数据线 | 需要 App 前台 | 数据来源 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **C 云端自动** | 默认方案；人不在电脑前、用 iPhone/iPad 盯盘 | 不要 | 不要 | 要 | 公开行情接口（GitHub Actions 定时产出） |
| **A USB 一键** | 设备没外网、或用本地通达信数据兜底 | 要 | 要 | 要 | 本机通达信/本机生成 |
| **B 局域网直推** | 人在电脑前但不想插线 | 要（且与设备同 Wi-Fi） | 不要 | 要 | 同上 |

三者可并存，互不冲突：谁先写进去，App 都会热刷新。

## 3. 通道 C：云端自动（无需电脑）

**流水线**：`.github/workflows/sync-live-db.yml`

- 触发：`cron`（UTC `03:00` / `06:30` / `07:05` = 北京 11:00 / 14:30 / 15:05，周一至周五）；
  另外 `src/live_db_builder.py` / 该 workflow 自身变更 push 时也会跑一次；Actions 页面可手动 `Run workflow`。
- 产出（**schema 2 分片布局**）：`live/manifest.json` + `live/bucket_<id>.db`，
  **强制覆盖式发布到 `data` 分支**（孤儿提交，仓库体积恒定）。不再依赖 `symbols.txt`（云端自行枚举全市场）。
- 下载地址（匿名可访问）：
  - 主源：`https://raw.githubusercontent.com/SunChuquin/Kline/data/live/manifest.json`
  - 备源：`https://cdn.jsdelivr.net/gh/SunChuquin/Kline@data/live/manifest.json`
  - 分片文件与 manifest **同目录**（App 按 manifest 里每个分片的 `file` 字段拼接）。
- 兼容：App 会先试旧布局 `<base>/tdx_live.manifest.json`，再试新布局 `<base>/live/manifest.json`；
  旧版 manifest（`schema` 缺失 / 为 1）仍按「整文件下载 + 原子替换 `tdx_live.db`」处理，升级瞬间不会失联。
- 生成失败 / 自检不通过 → job 失败，**不覆盖**上一版产物。

**设备侧**（设置 → 本地更新 → 「数据同步」）：

1. 「启用自动更新」**默认已开启**（随时可关）；
2. 数据源地址默认就是上面两条（按顺序回退），可改成自建镜像；
3. 更新时刻默认 `11:00, 14:30, 15:05`，可编辑；
4. 到点后 App 自动：取 manifest → **按自身缺口选片** → 逐片下载 → **sha256 校验** → 合并进本地增量库
   → 裁剪冗余 → 一次性热刷新（详见 §6）；
5. 也可点「立即更新」手动跑一次（同样受启用开关约束）。

> 语义提醒：**11:00 / 14:30 是盘中快照**（当日K线可能未完成），**15:05 是当日完整K线**。
> 面板上的「数据版本」会显示 `vN（YYYYMMDD）`，`YYYYMMDD` 是行情源给出的**真实交易日**，不是本机日期。

## 6. 分片机制与「按缺口取片」

### 6.1 云端分片（生成端契约，两端必须一致）

- **分片 id 算法**：`id = floor(days_since_1970(YYYYMMDD) / 14)`；
  例：`days_since_1970(20260922) = 20729` → `id = 1480`（以整数天数 / unix 秒为准，不依赖本地时区）。
- **一片覆盖 14 个自然日**（≈10 个交易日；边界长期稳定，不随窗口滑动漂移），最多保留**最新 10 片**（≈5 个月）。
- **分片间不重叠日期**（同一 `date` 只落一个分片）→ 「缺某片 = 缺那段区间」语义简单。
- 每片只含 `daily / weekly / monthly` 三表（周/月线用**整个保留窗口的日线**聚合，跨片仍正确；季/年线不发布）。
- 分片文件内表名：`bkt_meta / bkt_daily / bkt_weekly / bkt_monthly`（字段顺序与本地 `live_*` 一致）。
- manifest（schema 2）：

```json
{"schema": 2, "generated_at": 1790048739, "trade_date": 20260922,
 "source": "eastmoney", "symbols": 3611, "bucket_days": 14, "latest_bucket": 1480,
 "buckets": [
   {"file": "bucket_1480.db", "id": 1480, "min_date": 20260915, "max_date": 20260922,
    "bytes": 5242880, "sha256": "...",
    "rows": {"daily": 25277, "weekly": 3611, "monthly": 3611, "meta": 3611}}]}
```

### 6.2 设备侧「按缺口取片」确切规则

1. `needFrom` = 主库 `metaList` 中 `lastDate` 的**最大值**；**全部为空则退化为最早分片的 `min_date`**。
   （`needFrom` 缺失且分片也无 `min_date` → 选区为空，等价「无需下载」。）
2. `needTo` = 今天（**设备本地日期**，`YYYYMMDD`）。
3. 选出所有满足 `min_date <= needTo && max_date >= needFrom` 的分片 → **按 id 从新到旧** → **上限 10 片**。
4. **一片都不需要**（主库已新于所有分片）→ 跳过下载，标记成功并在面板「本次下载」显示
   「主库已是最新，无需下载分片」。
5. 逐片**串行**：下载到临时文件 → sha256 与 manifest 该片声明比对 → 交给 `LiveDataStore.mergeBucket`
   合并进本地增量库（`INSERT OR REPLACE`，同 `date` 以新分片为准）→ 临时文件删除。
6. **任一片失败 → 整体失败**：保留已合并的片与本地增量库原状，错误文案写明「第几片（id/文件名）+ 原因」。
7. 全部成功 → **裁剪**：删除本地增量中 `date <= needFrom` 的行（主库已有，留着纯属冗余；`needFrom` 缺失则不裁剪）
   → **一次性** `reloadAsync()` 热刷新（App 全程只刷一次）。

体积：全市场（≈3611 只）× 14 天 ≈ **5MB/片**；典型每次只需 1~2 片（主库停在 08-28、今天 09-22 时需 2 片）。

## 7. 合并到 tdx.db（可选，写回主库）

目的：让**主库本身**也变新（重开 App 后即使没有增量库也不缺数据），并让下一次「按缺口取片」的缺口变 0~1 片。

1. 面板「数据同步 → 合并到 tdx.db」：`同步中` / 增量库不可用 / 无可合并行 时按钮禁用；
2. 点按钮**先在后台算好**预估（写入根数 / 覆盖标的数 / 最新交易日），再弹**二次确认**；
3. 确认后（**全程在 `DatabaseManager.dbQueue` 上、单事务**）：
   1) 读主库 `meta` 建 `code → meta_id`（`code` 重复时取 `id` 最小者，并把歧义条数报出来）；
   2) 在 `LiveDataStore` 队列上把增量三表取成快照（**避免跨队列嵌套**），再回到 dbQueue 写；
   3) 对 `daily/weekly/monthly`：先探测主库是否存在该表，存在才逐行
      `INSERT OR REPLACE INTO <表>(meta_id,date,open,high,low,close,vol,amo) VALUES(?,?,?,?,?,?,?,?)`
      （prepared statement 循环 bind，绝不逐行拼 SQL）；**主库缺的表直接跳过**；
   4) 更新 `meta.last_date`（该 code 在增量里的最大 date）；
   5) 提交并返回统计：写入行数 / 命中标的数 / 跳过（主库无此 code）数 / 歧义 code 数 / 最新交易日。
4. **失败自动 `ROLLBACK`**：主库与增量库都保持原样，只回报失败原因。
5. 合并**不删除**主库任何历史行（只按主键 UPSERT）。
6. 合并完成后：增量库裁剪为**最新 3 个交易日**作缓冲 → `reloadAsync()` 热刷新；同时重读 `metaList`
   （否则下次按缺口取片会按旧的 `lastDate` 重复下载）。

风险与边界：

- 1.4GB 主库上的 UPSERT 走主键索引，量级为几万行 → **秒级**完成；仍保留「二次确认 + 事务」防误操作。
- 合并期间**独占 dbQueue**，禁止并发查询；不做网络 / 长文件 IO（增量快照在进入事务前已取好）。

## 8. 改关注标的清单

**全市场模式（默认）下**：云端自行枚举 A 股 + 指数（约 3611 只），**不再读 `symbols.txt`**，清单不会漂移。
`symbols.txt` 仍保留，仅用于小范围调试 / 私人清单模式（生成端 `--symbols` 选项）：

```
600519            # 贵州茅台（纯代码行；# 开头整行注释）
000001
999999            # 通达信口径的上证指数
600519 secid=1.600519   # 也支持显式指定行情源 secid
```

改完 `git push` → 流水线的 push 触发会立刻重新生成并发布（也可等下一个定时点）。
清单纯代码、不放备注以外的东西（仓库是 Public）。

## 9. 状态核对与故障排查

**设备侧状态**（Kline 前台时）：

```powershell
# 经 USB 转发后直接查（或把 127.0.0.1 换成设备局域网 IP）
Invoke-WebRequest http://127.0.0.1:5051/sync/status -UseBasicParsing
# → {"available":true,...,"metaCount":3611,"dailyCount":25277,"latestDate":20260922,"earliestDate":20260915,"reloadCount":1}
```

| 现象 | 原因与处理 |
| :--- | :--- |
| `available:false` | 增量库还没写进去（首次）→ 跑通道 C 的「立即更新」，或通道 A/B 推一次 |
| 推完状态不变 | App 不在前台/被锁屏（5051 无响应）；或忘了通知热刷新 → 通道脚本会自动 `POST /sync/reload` |
| 云端拉取一直失败 | 看面板「失败原因」：多为网络不通/镜像地址错；主源超时会自动换备源 |
| 似乎「每次都在重新下载分片」 | 正常：缺口按**主库** `last_date` 算；点了「合并到 tdx.db」后主库前移，缺口才会归零 |
| 面板「本次下载」显示「主库已是最新」 | 主库已新于所有保留分片 → 主动跳过（正常省流量行为） |
| 合并报「已回滚」 | 主库被占用/表结构不符 → 主库与增量库都保持原样，按提示文案排查后重试 |
| 刷新后K线没变化 | 该标的可能不在分片窗口内；或本次生成的数据与上一版相同（非交易日/未开盘） |
| 假期会不会多一根K线 | 不会：当日K线的日期来自行情源时间戳，非交易日不会新增（已用 `--now-date 20261001` 模拟验证） |

**查设备日志**：热刷新链路会打 `[Live]` / `[DB] dataVersion → n` / `[TdxSync]` / `[Merge]` 四组日志，
经 USB 用 `deploy_kline_to_ipad.py --pull-logs` 拉公共日志查看。

## 10. 硬边界

- **必须前台未锁屏**：iOS 无后台能力（TrollStore 版同样），所有通道的生效前提都是 App 在前台；
  这也是本方案能接受的前提——盯盘时 App 本来就开着。
- **主库默认不动**：1GB+ 的 `tdx.db` 仍按老办法手动整库替换（替换后需重启）；
  自动化的只有「增量」这一层，**写回主库是用户在个人中心显式点「合并到 tdx.db」的动作**（单事务 + 二次确认）。
- **季/年线不发布**：增量只含日/周/月线，季/年线视图回落主库（最新未完成周期可能滞后，属可接受取舍）。
- **并发安全**：设备侧同一时刻只允许一个同步在跑；失败一律保留上一版、不留半成品文件；
  「合并到主库」独占 `dbQueue` 单事务，失败自动回滚。
