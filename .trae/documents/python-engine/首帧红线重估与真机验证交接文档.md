## 二、「首帧红线是否可以移除」专项评估

### 2.1 红线是什么、为什么立

- **内容**（2026-10-04 用户决策，可行性分析 §8 修订第 6 条）：App 启动第一屏 K 线图渲染链路（含首屏指标计算）不依赖 Python 引擎。
- **依据**：① 真机 Py_Initialize 76~116ms 不可接受进首帧；② 降级矩阵硬约束——引擎未就位时首屏功能必须照常可用（否则「刚装完 App = 图表画不出指标」）。
- **重估通道**（同一决策预留）：实测「引擎常驻预热 + 近似计算不依赖 numpy + 150 根桥接往返落阈值内」三者齐备方可重估。

### 2.2 评估依据（当前证据链）

| 证据 | 数据 | 来源 | 指向 |
| --- | --- | --- | --- |
| 引擎初始化一次性成本 | 模拟器 46ms；真机历史 76~116ms | 实验 A-① / Phase-0 | 常驻预热后**完全移出用户链路**，障碍消除 |
| numpy import 一次性成本 | 模拟器 525ms；真机预估 3~10s | 实验 A-② | 同上（启动后台异步预热） |
| 稳态单次桥接开销 | 模拟器 median 14.2ms | 实验 B | **唯一剩余关键项**，真机待测 |
| 纯计算 | 0.34ms（150 根，真机已测） | Phase-0 实验 2 | 从来不是瓶颈 |
| 内存代价 | +25MB phys_footprint（模拟器） | 实验 B | 2GB 设备可接受，需监测 jetsam |
| 未就绪兜底 | isReady 门 + Swift 现状路径 | 模块 5 范式 + 降级轮全量验证 | 冷启动窗口无感回退 |

### 2.3 风险分析

| 风险 | 等级 | 分析 | 缓解 |
| --- | --- | --- | --- |
| **A8 性能不达标** | 高（核心风险） | 模拟器 14.2ms × 5~10 倍 = 70~150ms，大概率超 33ms 上限 | 这就是为什么**红线决策必须等真机数据**；不达标则红线维持，零损失（现状即 Swift） |
| 大序列序列化开销增长 | 中 | 实验 B 是 150 根；生产单屏可能 500~2000 根（IndicatorPipeline 预取 500 根/块），JSON 序列化/临时文件随根数线性增长 | 待执行项 #5：模拟器先跑 1000/2000 根压力曲线；必要时分块或改输入编码 |
| 内存压力/jetsam | 低-中 | +25MB 常驻；iPad mini 4 有 2GB | 实验④已采 phys_footprint；观察期监测后台存活率 |
| 多指标并帧预算 | 中 | 单次 call 批量算多指标（实验 B 已是 4 指标一次 call）没问题；但若首屏多个图表区域各自发起 call，耗时会叠加 | 切换设计必须**单屏合并为一次 call**（op="functions" 天然支持批量 calls） |
| 桥接临时文件 IO 在 A8 上更慢 | 已包含 | 实验 B 的 14.2ms 已含临时文件往返，真机倍数同样适用 | 无需单独缓解，随真机数据一并验证 |
| 引擎损坏/未装冷启动 | 低 | isReady 门天然回退 Swift | 已有降级轮全量验证 |

### 2.4 可行性结论（分档，以真机实验④ median 为准）

| 真机 median | 结论 | 动作 |
| --- | --- | --- |
| **< 16ms** | 红线可松动 | 进入 §2.5 技术调整方案实施（仍分阶段、可回滚） |
| **16 ~ 33ms** | 勉强可用，条件松动 | 需补两项评估再决策：① 单屏实际指标 call 次数与「打开图表→首屏可见」总预算（用户感知阈值，需用户拍板）；② 大序列压力数据（#5） |
| **≥ 33ms** | 红线维持 | 归档实验结论；候选 2 阶段 B 继续搁置；无任何损失（首帧现状即 Swift） |

### 2.5 对应的技术调整方案（红线松动后实施）

架构一句话：**启动后台预热（引擎 + numpy）+ 首帧指标 Python 优先 + isReady 门 Swift 兜底**。

分阶段（每阶段独立可编译可回滚，沿用项目标准打法）：

**阶段 R1 —— 启动预热钩子**
- `KlinePythonBridge.ensureOnce()` 现为惰性（首个调用点触发）；改为 App 启动完成后即后台触发（`ensureReady` 成功后追加一次 mytt 空转调用预热 numpy，结果丢弃）。
- 约束：预热必须 `DispatchQueue.global(qos: .utility)` 后台异步，绝不阻塞启动主线程；预热完成前一切调用照旧走 isReady 门。
- 验收：冷启动主线程无可感知卡顿（启动耗时打点对比无回归）；启动后数秒内沙盒日志出现 ensureReady 成功 + mytt 预热记录。

**阶段 R2 —— 首帧指标调用点切换**
- 落点：首屏指标计算入口（现状 Swift 路径）前置 Python 分支，**范式逐行照抄** `WatchlistSyncManager.currentPeriodBarsViaPython`：isReady 门（未就绪 → ensureOnce + 走 Swift）→ blockingCall（仅后台线程）→ 解码失败/超时 → 降级 Swift 原路径。
- 硬约束：单屏合并为一次 call（批量 calls）；序列长度上限与分块策略依据 #5 压力数据定；主线程直调 blockingCall 会 assert 崩溃（桥接层保护，勿绕过）。
- 验收：引擎轮/降级轮全量绿；沙盒日志确认首帧走 Python 的命中记录；真机首屏肉眼无卡顿（用户验收）。

**阶段 R3 —— 观察期与打点**
- 既有 `[PyBridge] <script>.py 完成（xxms）` 日志天然是打点；观察期（建议 1~2 周日常使用）监测 p95 漂移、降级触发率、jetsam。
- 回滚：isReady 门即天然回滚开关——引擎不装/移除即全程 Swift，无需代码回退。
